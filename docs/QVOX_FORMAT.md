# QVox 格式规范 — v1

> **单一文件。单一数据流。每条事实只存一次。**
>
> 一个从第一性原理出发构建的体素容器：PNG 的块流、GLB 的 JSON 前置布局、
> SPZ 的列式打包、FlatBuffers 的零解析访问。不继承任何现有体素格式的结构。

---

## 0. 设计原则

五条规则，其余一切由此推导。

| # | 原则 | 学自 | 推论 |
|---|---|---|---|
| **P1** | **整个文件就是一条带类型的块流，别无其他** | PNG / GLB | 文件即块。新功能 = 新块类型。旧读者遇到就跳过。 |
| **P2** | **每条事实只存一次** | ——（第一性原理） | 任何字段不得可由其他字段推导。不存可数出来的计数。 |
| **P3** | **元数据用 JSON，负载用列式二进制** | GLB / SPZ | 人读头部，机器读打包的列；压缩率提升 3–5×。 |
| **P4** | **块头自足：读到块头即知全部** | FlatBuffers | 长度、类型、校验值都在 payload 之前。 |
| **P5** | **缓存是派生的，且可证明可删除** | SPZ / FlatBuffers | 能重算的块就标明"可重算"，与其来源校验，且删之无害。 |

## 1. 容器

一个 `.qvox` 文件 = 8 字节签名 + 一个或多个块（第一个必须是 `HEAD`）。
文件在最后一个块结束时结束，没有终止符。

```
89 51 56 4F 58 0D 0A 1A        ← 签名
[HEAD] [块] [块] ...           ← 直至文件尾
```

### 1.1 签名（8 字节）

```
0x89 0x51 0x56 0x4F 0x58 0x0D 0x0A 0x1A
 │    │  │  │  │  │    │    │    └─ 0x1A  文件尾守护
 │    │  │  │  │  │    │    └────── 0x0A  LF
 │    │  │  │  │  │    └─────────── 0x0D  CR
 │    │  └──┴──┘  │    └──────────── 0x58  'X'
 │    │  "QVOX"   └───────────────── 0x4F  'O'
 │    └───────────────────────────── 0x51  'Q'（最高位置 1）
 └────────────────────────────────── 0x89（最高位置 1）
```

首尾的 `0x89`/`0x1A` 保证 7 位传输与文本模式转换都会破坏它并当场校验失败，
而不是加载出垃圾。一个不可能被偶然写错的字节序列。

### 1.2 块

每一个块，无一例外：

```
uint32  length      负载字节数
char[4] type        4 个 ASCII 字符
uint32  crc32       CRC32(length 字段的 4 字节 ‖ type ‖ payload)
byte[]  payload     length 字节，零填充到 4 字节边界
```

每块固定 12 字节开销，**全部位于 payload 之前**。读者读到块头即掌握
"多长、是什么、校验值"，无需读完 payload 才能校验（P4）。

**CRC 覆盖 `length` 本身**，因此块的边界也被校验：一个被截断或长度字段损坏的
块会被当场发现，而不是读出一段看似合法的垃圾。校验范围是
`length 的 4 个字节 ‖ type 的 4 个字节 ‖ payload`（填充不计入）。

读者遇到不认识的 `type` 时，**跳过 `length` 字节继续读**——这就是 P1，
也是整个前向兼容能力的全部。未知块**永远不算错误**。

块从 4 字节对齐处开始。填充字节为零，且**不计入** `length`。

**文件最少包含一个块**（即 `HEAD`）；只有签名、没有块的文件不合法。

## 2. 块类型

v1 共五种类型。这个集合应当缓慢增长，且每次增加都需要理由。

| 类型 | 数量 | 必需 | 可删 | 用途 |
|---|---|---|---|---|
| `HEAD` | 恰好 1 个 | ✅ 必须第一 | ❌ | 声明文件。JSON。 |
| `MATE` | ≤ 1 | 否 | ❌ | 材质调色板。 |
| `VOX0` | ≥ 0 | 否* | ❌ | 体素数据。每个模型一个。 |
| `NODE` | ≤ 1 | 否 | ❌ | 场景图、变换、动画。JSON。 |
| `CACH` | 任意 | 否 | ✅ | 任何可重算的数据。 |

\* 没有 `VOX0` 的文件是合法的——例如一个纯资产数据库。渲染器需要关心的
体素场景至少有一个。

删除全部 `CACH` 块后，文件必须加载出**完全相同的结果**——只是首次加载更慢。
这由 §6 强制保证。

## 3. `HEAD` —— 唯一的必填块

**`HEAD` 的 payload 就是一段 UTF-8 JSON，没有二进制前缀。** 这是文件的全部自描述。

之所以能如此干净：块头的 `length` 已给出 payload 字节数，因此无需再存一个
`json_length`——那是可由块头推导的事实（P2）。版本则在 JSON 的第一个键里。

### 3.1 HEAD JSON

```json
{
  "qvox": 1,
  "channels": [ { "name": "material", "bpp": 16 } ]
}
```

上面是**最小合法 HEAD**。完整示例：

```json
{
  "qvox": 1,
  "up_axis": "y",
  "block_size": 32,
  "bounds": { "min": [-1024, 0, -1024], "max": [1024, 256, 1024] },
  "channels": [
    { "name": "material", "bpp": 16 },
    { "name": "sdf",      "bpp": 8  }
  ]
}
```

| 键 | 必需 | 缺省 | 含义 |
|---|---|---|---|
| `qvox` | ✅ | —— | 规范版本。**必须是第一个键**，让读者一眼即能判断兼容性。 |
| `channels` | ✅ | —— | 有序通道列表。**`channels[0].name` 必须为 `"material"`。** |
| `up_axis` | 否 | `"y"` | `"x"`、`"y"` 或 `"z"`。 |
| `block_size` | 否 | `32` | VOX0 的空间分块尺寸，**必须是 2 的幂**。 |
| `bounds` | 否 | 无界 | 有界世界才写。缺省表示无界。 |

`bounds.min` 与 `bounds.max` 为体素坐标，**半开区间** `[min, max)`：`max` 不含。
范围之外不得出现非空体素。两个数组均为 `[x, y, z]`。

**缺省才是常态**：最常见的文件只需要 `qvox` 与 `channels` 两个键。

**没有任何字段重述另一个字段。** 没有 `format`（签名已说明），没有 `version`
（`qvox` 键已说明），没有 `material_count`（数 `MATE` 条目即可），没有
`voxel_count`（需要时累加即可），没有 `model_count`（数 VOX0 块即可），
没有 `animated`（`NODE` 里的 `animations` 已说明）。

> **为什么用 JSON 而非二进制字段？** 因为新增一个可选字段**绝不应导致版本号变化**，
> 并且人能直接用文本编辑器读懂头部。
>
> 写入方可额外加入任何自有键（如署名、时间戳、工具名）。读者**忽略未知键**，
> 因此这些键不构成格式的一部分，也永远不会破坏兼容性。

## 4. `MATE` —— 材质

仅当文件拥有多于一种材质时存在。列式（P3）。

```
uint16  entry_count
entry[] entry_count × 16 字节
```

### 4.1 条目（16 字节定长 → 以 `index × 16` 随机访问）

```
uint32  rgba          R<<24 | G<<16 | B<<8 | A
uint8   metal         0–255
uint8   rough         0–255
uint8   emission      0–255
uint8   trans         0–255
float32 hardness      物理：破坏
float32 mass          物理：崩塌
```

- **条目 0 保留且全零。** 体素值 `0` 表示空气。
- 因此 **体素值 == 材质索引** 无条件成立。
- `hardness` 兼具抗破坏性与连接强度，`mass` 驱动崩塌。**两个物理量足够**——
  一个体素需要三个物理常数的格式是过度规定的。

> 条目大小是常量 16，由 `qvox` 版本定义，**不写入文件**（P2）。
> 16 字节定长 → 读者一次乘法即可索引材质。无偏移、无变长、无名称块。
> 材质名属于编辑器元数据，不属于渲染必需数据；需要时写入方将其放入 HEAD JSON
> 的自有键，格式核心不为其引入变长结构。

## 5. `VOX0` —— 体素数据

列式、按块分组、自压缩。

```
uint16  model_id          模型编号，供 NODE 的 kind="model" 节点引用
uint32  block_count
block[] block_count × block（§5.1）
```

`model_id` 为 `uint16`，因此文件最多可容纳 65536 个模型。它是体素数据的**编号**，
由写入方分配；`NODE` 中 `kind="model"` 的节点以同一个数值引用它。字段间不做
填充对齐——payload 按字节寻址，无需对齐（P2：不为对齐引入无意义的填充字节）。

### 5.1 块

```
int32   bx, by, bz        块坐标（体素 >> block_size 的幂）
uint8   codec             块级编解码（§5.2）——先说明"是什么"
uint32  payload_length    负载字节数
byte[]  payload
```

字段顺序与外层块头同构：先身份（`codec` / 坐标），再长度，最后负载。
与顶层块头一样，**长度在负载之前**（P4）。

> 块头共 17 字节（`3×int32 + uint8 + uint32`），不是 4 的整数倍。这**不是疏漏**：
> `codec` 只有 1 字节，若为凑对齐而给它补 3 字节填充，就等于让每个块平白多付
> 3 字节，违背 P2。负载按字节寻址，本就不需要对齐——**一致性优先于对齐**。

块尺寸取自 HEAD 的 `block_size`，**不在此重复存储**（P2）。

**列式方向**：对于通道 `[material, sdf]`，负载是
`[全部 material 值][全部 sdf 值]`——连续成段，**绝不**逐体素交错。
这是 P3，也是单项最大的压缩收益。

**块是局部性与编辑的单位。** 小到可以廉价重写，大到足以摊平头部开销。
只有非空块才会出现。

### 5.2 块级编解码

所有编解码都沿**与 `DENSE` 相同的顺序**遍历块内体素：`idx = x + y·B + z·B²`
（即 ZXY 外层、X 最快）。这一点对 `RUN` 尤为重要——游程沿该线性下标连续铺展。

| 编解码 | 值 | 负载 | 胜出场景 |
|---|---|---|---|
| `EMPTY` | 0 | *（无）* | 稀疏世界——绝大多数块 |
| `SOLID` | 1 | 每通道一个值 | 均匀填充 |
| `RUN` | 2 | `count` + `count ×(varint 游程长度, 值)` | 层状／条纹结构 |
| `DENSE` | 3 | 每通道 `B³ × bpp/8`，ZXY 顺序 | 高熵噪声 |
| `INDEXED` | 4 | `uint8 n` + n 个材质索引 + `B³ × ⌈log₂n⌉` 位 | 少量不同取值 |

`EMPTY` 与 `SOLID` 是整个性能故事的核心：真实数据里绝大多数块命中二者之一，
算上 17 字节的块头（`3×int32 + 1×uint8 + 1×uint32`）与近乎为零的负载，
每块仅约 17 字节。写入方挑选最小的编解码；读者按字节分发。

> **`INDEXED` 不携带材质值本身**，只携带**指向 `MATE` 的索引**（`n ≤ 255`）。
> 材质的真实内容在 `MATE` 中只存一次（P2）；`INDEXED` 只是在块内重复引用它们。
> 若文件无 `MATE`，则 `INDEXED` 不适用（改用 `DENSE`）。

## 6. `CACH` —— 派生数据

**由一条规则定义：`CACH` 块可以在任何时刻删除，语义影响为零。**

```
char[4] kind          任意的 4 字符标签，兼作命名空间，由写入方定义
uint32  source_crc    本缓存派生来源块的 CRC32
uint16  algo_version  派生算法在 `kind` 命名空间内的版本
byte[]  payload       余下的全部字节
```

三个字段共 10 字节**定长前置**，其后直到块尾即 `payload`——**由外层块头的
`length` 界定，内部不再重复存储**（P2）。读者从块头取 `length`，减去 10 个定长
字节，剩下的就是缓存内容；写入方亦然。这与 `HEAD`（整段 JSON 就是 payload）
是同一套读法，无需任何"回头引用块头做减法"的特殊规则。

**失效是自动且彻底的：**

1. `source_crc` ≠ 当前来源 CRC → 丢弃，重算。
2. `(kind, algo_version)` 组合读者不认识 → 丢弃，重算。
3. `kind` 不认识 → 丢弃。

> `algo_version` 的语义是"**在 `kind` 这个命名空间内**的算法版本"。不同写入方
> 使用各自的 `kind` 标签，因此它们的版本号互不冲突。

> 忽略所有 `CACH` 块的读者，产出与用满全部缓存的读者**完全相同**——只是
> 预热更慢。这不是约定，而是这个块类型的定义。

由于缓存绝不持有其来源中不存在的信息，本格式不存在"这是权威数据还是过期数据？"
这个问题。整整一类 bug 被设计掉了。

`kind` 的含义完全由写入方与读者商定——格式本身不解释它。一个常见的用法是让
写入方缓存自己渲染器所需的任何中间结果（例如某种降采样、简化网格、查询加速
结构），并在源数据变更时自动作废。格式对此保持中立。

## 7. `NODE` —— 场景图与动画

一个 JSON 块。以任何语言都能解析的形式取代 `.vox` 的 `nTRN`/`nGRP`/`nSHP` 三件套。

```json
{
  "nodes": [
    { "name": "root",  "kind": "group", "children": [1, 2] },
    { "name": "body",  "kind": "model", "model_id": 0, "transform": { "t": [0,0,0], "r": 0, "s": [1,1,1] } },
    { "name": "wheel", "kind": "model", "model_id": 1, "transform": { "t": [4,0,0], "r": 0, "s": [1,1,1] } }
  ],
  "layers": ["default"],
  "animations": [
    { "name": "spin", "loop": true,
      "frames": [ { "t": 0, "2": { "r": 4 } }, { "t": 100, "2": { "r": 8 } } ] }
  ]
}
```

- **节点是数组；身份即位置。** 没有 `id` 字段——下标就是 id。这去掉了一个字段
  以及整整一类悬空引用 bug。`animations` 的 `frames` 同样以**节点下标**为键
  （上例 `"2"` 即 `wheel`），全文件只有一种寻址方式。节点名是给人看的、
  可选的标签，从不参与寻址。
- `r` 是旋转索引 **0–23**（24 种轴对齐朝向），与 `.vox` 相同的编号，因此导入的
  旋转是精确的。
- `kind`：`"group"`（变换容器）或 `"model"`（通过 `model_id` 绑定一个 `VOX0`，
  其值等于该 `VOX0` 的 `model_id` 字段）。
- **单个静态模型可整块省略。** 静态场景可省略 `animations`。**缺省才是常态，且零成本。**

## 8. 读取一个文件

```
1. 读 8 字节。匹配签名，否则拒绝。
2. 读第一个块。其类型必须是 "HEAD"。
3. 解析其 payload 为 JSON。此时你已掌握全部结构性信息。
4. 遍历各块：
     MATE → 材质
     VOX0 → 体素（每个 model_id 一个）
     NODE → 场景图
     CACH → 忽略，或用于加速
     ???? → 跳过 length 字节
```

**零解析访问（P4）**：块头自带长度与校验值，因此跳过或校验任意块都只需读
其块头。带缓存的写入方可额外提供一份目录缓存（一个 `CACH`）来实现 O(1) 查找；
没有它，线性扫描也能到达同一个块。两者都正确。

**渐进加载**：JSON 元数据位于负载之前，因此客户端可以在读取任何体素之前就呈现
场景图与材质。

**流式读取**：读 `HEAD`，然后只读取那些与视野相交的 `VOX0` 块。

## 9. 完整性

| 层级 | 校验 | 失败处理 |
|---|---|---|
| 文件 | 8 字节签名 | 拒绝 |
| 块 | 逐块 CRC32（覆盖 `length` + `type` + payload，位于块头） | 跳过该块，保留其余 |
| 缓存 | `source_crc` + `(kind, algo_version)` | 丢弃缓存，重算 |

**没有文件级校验和，这是刻意的**：块可被独立校验，因此一处损坏不会牵连其余部分。

## 10. 对比

| | `.vox` | **`.qvox`** |
|---|---|---|
| 容器 | 嵌套块树 | **扁平块流** |
| 头部 | 临时性的 4 字符标签 | **JSON，可扩展，单一真相源** |
| 布局 | 行式 | **列式** |
| 最大尺寸 | 256³ | **无界** |
| 颜色 | 256 项调色板 | **完整 RGBA + PBR + 物理** |
| 场景图 | nTRN/nGRP/nSHP | **JSON `NODE`** |
| 完整性 | 无 | **逐块 CRC32（块头）** |
| 扩展 | 新标签 | **新块类型，跳过安全** |

## 11. 为什么它既精简又强大

**精简** —— 承重规则一屏即可写完：文件 = 签名 + 块流；块 = 长度、类型、CRC、负载；
`HEAD` 就是一个 JSON 块；五种块类型；每条事实只存一次。

**强大：**
- 列式比行式压缩好 3–5×（SPZ 的结论）。
- JSON 元数据意味着新字段永不破坏旧读者。
- 逐块 CRC 提供部分恢复能力。
- 缓存被定义为可删除，因此不存在过期数据的歧义。

**快：**
- `EMPTY`/`SOLID` 让常见块仅约 17 字节且解码 O(1)。
- 2 的幂块尺寸让坐标运算全走位移。
- 块头自足，读到块头即可校验与跳过，永不二次扫描。

## 12. 完整示例 —— 一个 64³、3 材质的模型

```
89 51 56 4F 58 0D 0A 1A                              签名

[HEAD]                 length=115 type="HEAD" crc32=…   （JSON 共 115 字节，此处已 4 字节对齐）
  { "qvox":1, "block_size":32, "bounds":{"min":[0,0,0],"max":[64,64,64]},
    "channels":[{"name":"material","bpp":16}] }

[MATE]                 length=50 type="MATE" crc32=…
  entry_count=3                              （2 + 3×16 = 50 字节）
  entry[0] = 全零                              （空气：rgba=0，物理量=0）
  entry[1] = rgba=FF808080 metal=0   rough=200 emission=0 trans=0 hardness=8.0 mass=2.5
  entry[2] = rgba=FFFFD700 metal=255 rough=80  emission=0 trans=0 hardness=3.0 mass=9.1

[VOX0]                 length=168 type="VOX0" crc32=…
  model_id=0 block_count=8                        （6 + 8 块 = 168 字节）
    (0,0,0) EMPTY                                 →  17 字节
    (1,0,0) SOLID   material=1                    →  19 字节
    (0,1,0) RUN     12 段游程                     →  41 字节
    … 其余 5 块（均为 EMPTY：5 × 17 = 85 字节）

[CACH]                 length=90 type="CACH" crc32=…
  kind="mesh" source_crc=DEADBEEF algo_version=1  （10 + 80 字节负载，可删）
```

固定开销：8（签名）+ 4×12（块头）= 56 字节。上例各块负载合计 115+50+168+90 = 423 字节，
整个文件 **479 字节**——承载一个 64³、3 材质、8 个非空块的模型。其中体素负载仅
168 字节，是原始数据（64³×2 字节 ≈ 512 KB）的 **0.03%**。这就是列式 + 块级编解码的收益。

---

## 13. 实现说明

- **字节序**：小端。所有多字节字段。
- **变长整数**：LEB128，仅用于 `RUN` 负载内部的游程长度。
- **字符串**：UTF-8。JSON 的边界由所属块的 `length` 界定，**从不**以 NUL 结尾。
- **对齐**：块起始 4 字节对齐；负载零填充。
- **未知块**：按 `length` 跳过。**永远不算错误**。
- **前向兼容**：读到更高 `qvox` 版本的读者，仍可读取它能识别的块。它**只**应
  拒绝未知的*必需*块——而 v1 除 `HEAD` 外未定义任何必需块。

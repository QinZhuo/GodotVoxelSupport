# QVox 格式规范 — v1

> **单一文件。单一数据流。每条事实只存一次。**
>
> 一个从第一性原理出发构建的体素容器：PNG 的块流、GLB 的 JSON 前置布局、
> SPZ 的列式打包、FlatBuffers 的零解析访问。不继承任何现有体素格式的结构。

---

## 0. 设计原则

四条规则，其余一切由此推导。

| # | 原则 | 学自 | 推论 |
|---|---|---|---|
| **P1** | **整个文件就是一条带类型的块流，别无其他** | PNG / GLB | 文件即块。新功能 = 新块类型。旧读者遇到就跳过。 |
| **P2** | **每条事实只存一次** | ——（第一性原理） | 任何字段不得可由其他字段推导。不存可由 JSON 反映的标志位。不存可数出来的计数。 |
| **P3** | **元数据用 JSON，负载用列式二进制** | GLB / SPZ | 人读头部，机器读打包的列；压缩率提升 3–5×。 |
| **P4** | **缓存是派生的，且可证明可删除** | SPZ / FlatBuffers | 能重算的块就标明"可重算"，与其来源校验，且删之无害。 |

### v1 **不**包含什么

无空间嵌套。无 region 层级。无 LOD 层。无目录表。无调色板限色。无魔法填充。
无重复存储的字段。无重述他处已有事实的标志位。

---

## 1. 容器

一个 `.qvox` 文件 = 8 字节签名 + 零个或多个块。

```
89 51 56 4F 58 0D 0A 1A        ← 签名
[块] [块] [块] ...             ← 直至文件尾
```

文件在**最后一个块结束时结束**。没有终止符——最后一个块写完了，文件也就完了。

### 1.1 签名（8 字节）

```
0x89 0x51 0x56 0x4F 0x58 0x0D 0x0A 0x1A
 │    │  │  │  │  │    │    │    └─ 0x1A  文件尾守护（拒绝 DOS 文本模式"修正"）
 │    │  │  │  │  │    │    └────── 0x0A  换行 LF
 │    │  │  │  │  │    └─────────── 0x0D  回车 CR
 │    │  └──┴──┘  │    └──────────── 0x58  'X'
 │    │  "QVOX"   └───────────────── 0x4F  'O'
 │    └───────────────────────────── 0x51  'Q'（最高位置 1 → 7 位传输会失败）
 └────────────────────────────────── 0x89（最高位置 1）
```

与 PNG 同样的道理：一个不可能被偶然写错的字节序列；其中的 CR/LF 会被任何
粗暴的文本转换破坏，于是校验当场失败并大声报错，而不是加载出一堆垃圾。

### 1.2 块

每一个块，无一例外：

```
uint32  length      负载字节数
char[4] type        4 个 ASCII 字符
byte[]  payload     length 字节，零填充到 4 字节边界
uint32  crc32       对 type + payload 的 CRC32（不含填充）
```

每块固定 12 字节开销。读者遇到不认识的 `type` 时，**跳过 `length` 字节继续读**
——这就是 P1，也是整个前向兼容能力的全部。未知块**永远不算错误**。

块从 4 字节对齐处开始。填充字节为零，且**不计入** `length`。

---

## 2. 块类型

v1 共五种类型。这个集合应当缓慢增长，且每次增加都需要理由。

| 类型 | 数量 | 必需 | 可删 | 用途 |
|---|---|---|---|---|
| `HEAD` | 恰好 1 个 | ✅ 必须第一 | ❌ | 声明文件。JSON。 |
| `MATE` | ≤ 1 | 否 | ❌ | 材质调色板。 |
| `VOX0` | ≥ 0 | 否* | ❌ | 体素数据。每个模型一个。 |
| `NODE` | ≤ 1 | 否 | ❌ | 场景图、变换、动画。JSON。 |
| `CACH` | 任意 | 否 | ✅ | 可重算数据（LOD、网格、遮挡）。 |

\* 没有 `VOX0` 的文件是合法的——例如一个纯资产数据库。渲染器需要关心的
体素场景至少有一个。

删除全部 `CACH` 块后，文件必须加载出**完全相同的结果**——只是首次加载更慢。
这由 §6 强制保证。

---

## 3. `HEAD` —— 唯一的必填块

固定二进制前缀（让读者在解析文本之前就能做出判断），后接 JSON 正文。
**这是文件的全部自描述。**

```
uint16  spec_version     必须为 1
uint16  json_length      JSON 正文的字节长度（不含填充）
char[]  json             UTF-8，json_length 字节，零填充到 4 字节边界
```

二进制部分就这些。**其余描述文件的一切都只写在 JSON 里，只写一次。**
前缀与正文之间没有任何字段重复（P2）。

### 3.1 HEAD JSON

```json
{
  "qvox": 1,
  "generator": "GodotVoxelSupport/qvox 1.0",

  "up_axis": "y",
  "block_size": 32,

  "bounds": {
    "min": [-1024, 0, -1024],
    "max": [ 1024, 256, 1024],
    "unbounded": false
  },

  "channels": [
    { "name": "material", "bpp": 16 },
    { "name": "sdf",      "bpp": 8  }
  ]
}
```

| 键 | 必需 | 含义 |
|---|---|---|
| `qvox` | ✅ | 规范版本。**必须是第一个键**，让读者一眼即能判断兼容性。 |
| `up_axis` | ✅ | `"x"`、`"y"` 或 `"z"`。 |
| `block_size` | ✅ | VOX0 的空间分块尺寸，2 的幂。为建议值（读者可重新分块），非结构性。 |
| `bounds` | 否 | 无界世界可省略。`unbounded: true` 表示忽略 min/max。 |
| `channels` | ✅ | 有序通道列表。**`channels[0].name` 必须为 `"material"`。** |
| `generator` | 否 | 自由文本来源说明。读者**永不**解析它。 |

**这里没有任何字段重述另一个字段。** 没有 `format: "qvox"`（签名已说明），
没有 `version`（`qvox` 键已说明），没有 `material_count`（数 `MATE` 条目即可），
没有 `voxel_count`（需要时累加 VOX0 各块即可），没有 `model_count`（数 VOX0 块即可），
没有 `animated`（`NODE` 里的 `animations` 已说明），没有 `grid_origin`（`bounds` 已说明）。

> **为什么用 JSON 而非纯二进制？** 因为新增一个可选字段**绝不应导致版本号变化**，
> 并且人能直接用文本编辑器读懂头部。GLB 已验证这条路可行。二进制前缀只承担
> "JSON 有多长"——即定位文本所需的最小信息。

## 4. `MATE` —— 材质

仅当文件拥有多于一种材质时存在。列式（P3）。

```
uint16  entry_count
uint16  entry_size        必须为 20
uint32  names_length      名称块字节数
entry[] entry_count × entry_size
byte[]  names             UTF-8，NUL 分隔的名称，共 names_length 字节
```

### 4.1 条目（20 字节定长 → 以 `index × 20` 随机访问）

```
uint32  rgba          R<<24 | G<<16 | B<<8 | A
uint8   metal         0–255
uint8   rough         0–255
uint8   emission      0–255
uint8   trans         0–255
float32 hardness      物理：破坏
float32 mass          物理：崩塌
uint32  name_offset   名称块内字节偏移（0xFFFFFFFF = 无名）
```

- **条目 0 保留且全零。** 体素值 `0` 表示空气。
- 因此 **体素值 == 材质索引** 无条件成立。
- 物理属性（`hardness`、`mass`）以及旧设计中的"连接强度"已并入：
  `hardness` 兼具抗性，`mass` 驱动崩塌。**不再有第三个 float**——一个
  体素需要三个物理常数的格式是过度规定的。

> 20 字节定长 → 读者一次乘法即可索引材质。无偏移、无变长、无逐材质长度。
> 简单即快。

## 5. `VOX0` —— 体素数据

列式、按块分组、自压缩。

```
uint8   codec             负载级编解码（§5.3）
uint8   model_id          指向 NODE 模型的索引，或 0
uint16  block_size_po2    本块内实际使用的分块尺寸
uint32  block_count
block[] block_count × block（§5.1）
```

### 5.1 块

```
int32   bx, by, bz        块坐标（体素 >> block_size_po2）
uint32  payload_length
uint8   codec             块级编解码（§5.2）
byte[]  payload
```

**列式方向**：对于通道 `[material, sdf]`，负载是
`[全部 material 值][全部 sdf 值]`——连续成段，**绝不**逐体素交错。
这是 P3，也是单项最大的压缩收益。

**块是局部性与编辑的单位。** 小到可以廉价重写，大到足以摊平头部开销。
只有非空块才会出现。

### 5.2 块级编解码

| 编解码 | 值 | 负载 | 胜出场景 |
|---|---|---|---|
| `EMPTY` | 0 | *（无）* | 稀疏世界——绝大多数块 |
| `SOLID` | 1 | 每通道一个值 | 均匀填充 |
| `RUN` | 2 | `count` + `count ×(varint 游程, 值)` | 层状／条纹结构 |
| `DENSE` | 3 | 每通道 `B³ × bpp/8`，ZXY 顺序 | 高熵噪声 |
| `INDEXED` | 4 | `uint16 n` + n 项调色板 + `B³ × ⌈log₂n⌉` 位 | 少量不同取值 |

`EMPTY` 与 `SOLID` 是整个性能故事的核心：真实数据里绝大多数块命中二者之一，
每块约 8 字节。写入方挑选最小的编解码；读者按字节分发。

### 5.3 负载级编解码

负载级 `codec` 在 v1 中只定义了一个值：

| 值 | 含义 |
|---|---|
| `0` | 裸块——每块自带编解码（§5.2） |

预留给未来的整块变换（例如熵编码阶段）。它的存在意味着：将来增加一个只是
加一个值，而不是一次格式修订。

## 6. `CACH` —— 派生数据

**由一条规则定义：`CACH` 块可以在任何时刻删除，语义影响为零。**

```
char[4] kind          "lod1".."lod9"、"mesh"、"occ "、"toc " …
uint32  source_crc    本缓存派生来源块的 CRC32
uint16  algo_version  派生算法变更时递增
uint16  reserved      零
uint32  payload_length
byte[]  payload
```

**失效是自动且彻底的：**

1. `source_crc` ≠ 当前来源 CRC → 丢弃，重算。
2. `algo_version` 读者不认识 → 丢弃，重算。
3. `kind` 不认识 → 丢弃。

> 忽略所有 `CACH` 块的读者，产出与用满全部缓存的读者**完全相同**——只是
> 预热更慢。这不是约定，而是这个块类型的定义。

由于缓存绝不持有其来源中不存在的信息，本格式不存在"这是权威数据还是过期数据？"
这个问题。整整一类 bug 被设计掉了。

`toc` 缓存（目录表）也是一个 `CACH` 块——一个用于 O(1) 查找的可选索引。
它**同样**可删，这正是重点：**连索引都不承重**。

## 7. `NODE` —— 场景图与动画

一个 JSON 块。以任何语言都能解析的形式取代 `.vox` 的 `nTRN`/`nGRP`/`nSHP` 三件套。

```json
{
  "nodes": [
    { "name": "root",  "kind": "group", "children": [1, 2] },
    { "name": "body",  "kind": "model", "model": 0, "transform": { "t": [0,0,0], "r": 0, "s": [1,1,1] } },
    { "name": "wheel", "kind": "model", "model": 1, "transform": { "t": [4,0,0], "r": 0, "s": [1,1,1] } }
  ],
  "layers": ["default"],
  "animations": [
    { "name": "spin", "loop": true,
      "frames": [ { "t": 0, "wheel": { "r": 4 } }, { "t": 100, "wheel": { "r": 8 } } ] }
  ]
}
```

- **节点是数组；身份即位置。** 没有 `id` 字段——下标就是 id。这去掉了一个字段
  以及整整一类悬空引用 bug。
- `r` 是旋转索引 **0–23**（24 种轴对齐朝向），与 `.vox` 相同的编号，因此导入的
  旋转是精确的。
- `kind`：`"group"`（变换容器）或 `"model"`（通过 `model_id` 绑定一个 `VOX0`）。
- **单个静态模型可整块省略。** 静态场景可省略 `animations`。**缺省才是常态，且零成本。**

## 8. 读取一个文件

```
1. 读 8 字节。匹配签名，否则拒绝。
2. 读第一个块。其类型必须是 "HEAD"。
3. 解析 spec_version，再解析 JSON。此时你已掌握全部结构性信息：
   轴向、块尺寸、边界、通道。
4. 遍历各块：
     MATE → 材质
     VOX0 → 体素（每个 model_id 一个）
     NODE → 场景图
     CACH → 忽略，或用于加速
     ???? → 跳过 length 字节
```

**零解析访问（P4）**：块自带长度，因此跳到任意块只需跳过前面的块。若存在可选的
`toc` `CACH` 块，查找为 O(1)；没有它，线性扫描也能到达同一个块。两者都正确。

**渐进加载**：JSON 元数据位于负载之前，因此客户端可以在读取任何体素之前就呈现
场景图与材质。

**流式读取**：读 `HEAD`，然后只读取那些与视野相交的 `VOX0` 块。

## 9. 完整性

| 层级 | 校验 | 失败处理 |
|---|---|---|
| 文件 | 8 字节签名 | 拒绝 |
| 块 | 逐块 CRC32 | 跳过该块，保留其余 |
| 缓存 | `source_crc` + `algo_version` | 丢弃缓存，重算 |

**没有文件级校验和，这是刻意的**：块可被独立校验，因此一处损坏不会牵连其余部分。
整文件哈希严格来说更差——要么全对，要么全废。

## 10. 对比

| | `.vox` | **`.qvox`** |
|---|---|---|
| 容器 | 嵌套块树 | **扁平块流** |
| 头部 | 临时性的 4 字符标签 | **JSON，可扩展，单一真相源** |
| 布局 | 行式 | **列式** |
| 最大尺寸 | 256³ | **无界** |
| 颜色 | 256 项调色板 | **完整 RGBA + PBR + 物理** |
| LOD | —— | **派生 `CACH`，可删** |
| 场景图 | nTRN/nGRP/nSHP | **JSON `NODE`** |
| 完整性 | 无 | **逐块 CRC32** |
| 扩展 | 新标签 | **新块类型，跳过安全** |

## 11. 为什么它既精简又强大

**精简** —— 承重规则一屏即可写完：
- 文件 = 签名 + 一条块流。
- 块 = 长度、类型、负载、CRC。
- `HEAD` 是唯一必填块；它是带 4 字节前缀的 JSON。
- 五种块类型。每条事实只存一次。可推导的东西一律不存。

**强大：**
- 列式比行式压缩好 3–5×（SPZ 的结论）。
- JSON 元数据意味着新字段永不破坏旧读者。
- 逐块 CRC 提供部分恢复能力。
- 缓存被定义为可删除，因此不存在过期数据的歧义。

**快：**
- `EMPTY`/`SOLID` 让常见块约 8 字节且解码 O(1)。
- 2 的幂块尺寸让坐标运算全走位移。
- 块自带长度，因此永不需要二次扫描。

## 12. 完整示例 —— 一个 64³、3 材质的模型

```
89 51 56 4F 58 0D 0A 1A                              签名

[HEAD]                 type="HEAD"
  spec_version=1  json_length=142
  { "qvox":1, "up_axis":"y", "block_size":32,
    "bounds":{"min":[0,0,0],"max":[64,64,64],"unbounded":false},
    "channels":[{"name":"material","bpp":16}] }
  crc32

[MATE]                 type="MATE"
  entry_count=3 entry_size=20 names_length=12
  entry[0] = 00…00                     （空气）
  entry[1] = stone  rgba=FF808080 metal=0   rough=200 hardness=8.0 mass=2.5
  entry[2] = gold   rgba=FFFFD700 metal=255 rough=80  hardness=3.0 mass=9.1
  names    = "stone\0gold\0"
  crc32

[VOX0]                 type="VOX0"
  codec=0 model_id=0 block_size_po2=5 block_count=8
    (0,0,0) EMPTY                                 →   8 字节
    (1,0,0) SOLID   material=1                    →   8 字节
    (0,1,0) RUN     12 段游程                     →  ~30 字节
    … 其余 5 块
  crc32

[CACH]                 type="CACH"
  kind="lod1" source_crc=DEADBEEF algo_version=1   （可删）
  crc32
```

固定开销：8 + 5×12 = 68 字节。负载：由编解码决定——典型模型仅为原始数据的几个百分点。

## 13. 实现说明

- **字节序**：小端。所有多字节字段。
- **变长整数**：LEB128，仅用于 `RUN` 负载内部与长度前缀。
- **字符串**：UTF-8。JSON 为长度前缀且**从不**以 NUL 结尾；`MATE` 内的名称在其块内以 NUL 结尾。
- **对齐**：块起始 4 字节对齐；负载零填充。
- **未知块**：按 `length` 跳过。**永远不算错误**。
- **保留字段**：写零；读者忽略。
- **前向兼容**：读到更高 `spec_version` 的读者，仍可读取它能识别的块。它**只**应
  拒绝未知的*必需*块——而 v1 除 `HEAD` 外未定义任何必需块。

## 附录 A —— `.vox` 旋转索引（0–23）

24 种轴对齐朝向，索引 `0`–`23`，与 MagicaVoxel 编号一致，因此 `.vox` 旋转可精确
转换。本表是 `.vox` 对 QVox 的**唯一**贡献，而它是张常量表，不是一种结构。

# QVox 格式规范 — v2

> **定位**：`.qvox` 是一个**体素模型容器**，与 MagicaVoxel 的 `.vox` 同级——
> 可独立分发、可直接观察、可作为项目资产被编辑器导入的**源文件**，
> 不是烘焙中间产物或临时文件。同一个容器**也**能承载"整个世界存档"
> （多模型 + 增量写盘），但那是它的用法之一，不是它的身份。
>
> 配套实现（`addons/VoxelSupport/`）：
> - **格式内核** `QVoxSpec` / `QVoxBlockCodec` / `QVoxFile`（定义、编解码、读写与校验）
> - **资产导入** `VoxData.from_asset()`：`.vox` 与 `.qvox` 的统一入口 → 编辑器导入器
> - **世界存档** `QVoxStream`：可写、脏标记、增量落盘

> **单一文件。单一数据流。每条事实只存一次。**

---

## 0. 设计原则

五条规则，其余一切由此推导。

| # | 原则 | 学自 | 推论 |
|---|---|---|---|
| **P1** | **整个文件就是一条带类型的块流，别无其他** | PNG / GLB | 文件即块。新功能 = 新块类型。旧读者遇到就跳过。 |
| **P2** | **每条事实只存一次** | ——（第一性原理） | 任何字段不得可由其他字段推导。不存可数出来的计数。 |
| **P3** | **元数据用 JSON，负载用列式二进制** | GLB / SPZ | 人读头部，机器读打包的列；压缩率提升 3–5×。 |
| **P4** | **块头自足：读到块头即知全部** | FlatBuffers | 长度、类型、校验值都在 payload 之前。 |
| **P5** | **缓存是派生的，且可证明可删除** | SPZ / FlatBuffers | 能重算的块就标明"可重算"，与其来源校验，且删之无害。 |

## 1. 容器

一个 `.qvox` 文件 = 8 字节签名 + 一个或多个块（第一个必须是 `HEAD`）。
文件在最后一个块结束时结束，没有终止符。

```
89 51 56 4F 58 0D 0A 1A        ← 签名
[HEAD] [块] [块] ...           ← 直至文件尾
```

### 1.1 签名（8 字节）

```
0x89 0x51 0x56 0x4F 0x58 0x0D 0x0A 0x1A
 │    │  │  │  │  │    │    │    └─ 0x1A  文件尾守护
 │    │  │  │  │  │    │    └────── 0x0A  LF
 │    │  │  │  │  │    └─────────── 0x0D  CR
 │    │  └──┴──┘  │    └──────────── 0x58  'X'
 │    │  "QVOX"   └───────────────── 0x4F  'O'
 │    └───────────────────────────── 0x51  'Q'（最高位置 1）
 └────────────────────────────────── 0x89（最高位置 1）
```

首尾的 `0x89`/`0x1A` 保证 7 位传输与文本模式转换都会破坏它并当场校验失败，
而不是加载出垃圾。

### 1.2 块

每一个块，无一例外：

```
uint32  length      本块的字节数（含尾部填充）
char[4] type        4 个 ASCII 字符
uint32  crc32       CRC32(length 字段的 4 字节 ‖ type ‖ 负载的 length 个字节)
byte[]  payload    实际负载
byte[]  padding    0–3 字节的零，使 length 为 4 的倍数
```

**每块的总字节数 `length` 恒为 4 的倍数**，块头 12 字节也是 4 的倍数，因此
**所有块都在 4 字节对齐处开始**，无需任何额外计算。`length` 同时是"从本块头结束
到下一块头开始"的字节数——读者跳过任意块时，只需 `seek` 过 `length` 个字节，
**无论它是否理解该块**。这是 P1 与 P4 得以成立的唯一前提。

> **填充计入 `length`，这是刻意的。** 若把填充排除在外，读者就不得不每次做
> `(length + 3) & ~3` 的向上取整才能找到下一块——一个每个读者、每个块都要
> 重复的运算，而且**极易忘记**（忘记就错位 1–3 字节，读到填充当块头）。
> 把填充算进 `length`，跳过就永远是"跳过 length 个字节"这一件事。

每块固定 **12 字节块头开销**，全部位于 payload 之前。读者读到块头即掌握
"多长、是什么、校验值"，无需读完 payload 才能校验（P4）。

**CRC 覆盖 `length` 本身**，因此块的边界也被校验：一个被截断或长度字段损坏的
块会被当场发现，而不是读出一段看似合法的垃圾。校验范围是
`length 的 4 个字节 ‖ type 的 4 个字节 ‖ 负载的 `length` 个字节`——**填充字节计入 CRC**。

> **为什么填充也计入 CRC，而不是排除？** 因为 `length` 是校验范围的一部分，而
> `length` 已经包含填充。若 CRC 只覆盖"实际内容"，读取端就必须先知道"实际内容多长"
> 才能校验——可读取端拿到的只有 `length`，无法反推实际内容长度。把填充一并纳入，
> 读取端只需照 `length` 切一刀，"校验"与"跳过"用的是同一段字节，读写两端不可能
> 不一致。**CRC 的校验范围必须由读写两端都能独立推出的量唯一确定。**

读者遇到不认识的 `type` 时，**跳过 `length` 字节继续读**——这就是 P1，
也是整个前向兼容能力的全部。未知块**永远不算错误**。

**文件最少包含一个块**（即 `HEAD`）；只有签名、没有块的文件不合法。

## 2. 块类型

当前共五种类型。这个集合应当缓慢增长，且每次增加都需要理由。

| 类型 | 数量 | 必需 | 可删 | 用途 |
|---|---|---|---|---|
| `HEAD` | 恰好 1 个 | ✅ 必须第一 | ❌ | 声明文件。JSON。 |
| `MATE` | ≤ 1 | 否 | ❌ | 材质调色板。 |
| `VOX0` | ≥ 0 | 否* | ❌ | 体素数据。每个模型一个。 |
| `NODE` | ≤ 1 | 否 | ❌ | 场景图、变换、动画。JSON。 |
| `CACH` | 任意 | 否 | ✅ | 任何可重算的数据。 |

\* 没有 `VOX0` 的文件是合法的——例如一个纯资产数据库。渲染器需要关心的
体素场景至少有一个。

删除全部 `CACH` 块后，文件必须加载出**完全相同的结果**——只是首次加载更慢。
这由 §6 强制保证。

## 3. `HEAD` —— 唯一的必填块

**`HEAD` 的 payload 就是一段 UTF-8 JSON，没有二进制前缀。** 这是文件的全部自描述。

之所以能如此干净：块头的 `length` 已界定 payload 的边界，因此无需再存一个
`json_length`——那是可由块头推导的事实（P2）。版本则在 JSON 的第一个键里。
（JSON 的实际结尾由 JSON 解析器判定；块尾至多 3 个零填充字节在解析时被忽略。）

### 3.1 HEAD JSON

```json
{
  "qvox": 2,
  "channels": [ { "name": "material", "bpp": 16 } ]
}
```

上面是**最小合法 HEAD**。完整示例：

```json
{
  "qvox": 2,
  "up_axis": "y",
  "block_size": 32,
  "bounds": { "min": [-1024, 0, -1024], "max": [1024, 256, 1024] },
  "channels": [ { "name": "material", "bpp": 16 } ]
}
```

| 键 | 必需 | 缺省 | 含义 |
|---|---|---|---|
| `qvox` | ✅ | —— | 规范版本。**必须是第一个键**，让读者一眼即能判断兼容性。 |
| `channels` | ✅ | —— | 通道列表，每项 `{name, bpp}`，`bpp ∈ {8,16,32}`。**`channels[0].name` 必须为 `"material"`，且当前版本 `channels` 恰好 1 项。** |
| `up_axis` | 否 | `"y"` | `"x"`、`"y"` 或 `"z"`。出现其他值按缺省处理（不拒绝文件）。 |
| `block_size` | 否 | `32` | VOX0 的空间分块尺寸，**必须是 2 的幂**。 |
| `bounds` | 否 | 无界 | 有界世界才写。缺省表示无界。 |
| `require` | 否 | `[]` | 读者**必须理解**的块类型列表；无法处理其中任一者时应拒绝整个文件。 |

`bounds.min` 与 `bounds.max` 为体素坐标，**半开区间** `[min, max)`：`max` 不含。
范围之外不得出现非空体素。两个数组均为 `[x, y, z]`。

**通道约束：** 通道是**定长数值**通道，由 `name`（字符串）与 `bpp`
（每体素位宽，必须为 8、16 或 32）定义。`channels[0]` 为**支配通道**，
决定空块判定与渲染可见性（§5.2）。

**当前版本恰好支持 1 个通道**，即支配通道 `material`。读者遇到 `channels`
项数 ≠ 1，一律**拒绝整个文件**（`FATAL`），而**不是**按单通道猜测解码——
后者会"接受却读错"（例如 `RUN` 逐游程交错 `(len, material, sdf)`，只读
material 会从第二段起错位）。附加数据（如 `sdf`）应放入一个**独立块类型**，
这与 P1"新功能 = 新块类型"一致（同域的 MagicaVoxel `.vox` 同样只有单一体素
通道，附加信息全是独立 chunk）。将来确需多通道时，作为新的 `qvox` 版本引入
逐通道布局描述，格式核心不为它提前增加复杂度。

**缺省才是常态**：最常见的文件只需要 `qvox` 与 `channels` 两个键。

**没有任何字段重述另一个字段。** 没有 `format`（签名已说明），没有 `version`
（`qvox` 键已说明），没有 `material_count`（数 `MATE` 条目即可），没有
`voxel_count`（需要时累加即可），没有 `model_count`（数 VOX0 块即可），
没有 `animated`（`NODE` 里的 `animations` 已说明）。`require` 也不是重述——
它声明的是**读者必须理解什么**，而不是文件里**有什么**（那是块流本身说的）。

> **为什么用 JSON 而非二进制字段？** 因为新增一个可选字段**绝不应导致版本号变化**，
> 并且人能直接用文本编辑器读懂头部。
>
> 写入方可额外加入任何自有键（如署名、时间戳、工具名）。读者**忽略未知键**，
> 因此这些键不构成格式的一部分，也永远不会破坏兼容性。

## 4. `MATE` —— 材质

**存在条件：写入方的材质表非空时写入。** 材质表恒以下标 0 = 空气为起点
（条目 0 全零），因此"材质表非空"最弱也意味着"至少有一个空气条目"。

> **为什么不用"索引最大值 ≥ 1"作判据？** 那需要先扫遍所有体素才知道该不该写
> ——（a）写方多付一次全量扫描，（b）在流式写盘里"所有体素"根本不一次性可得。
> 把判据定为"材质表非空"，写方只需知道自己声明了几种材质即可决定，
> **O(1) 且与流式写盘相容**。代价是可能写入一份"当前没被任何体素引用"的材质表
> ——但这份表本就由写方持有、至多几百字节，且删掉后文件仍能正确加载。
> **多写一小段无引用数据，换写方不必全量扫描**，这是划算的。

若整个文件只有空气**且写方没有声明任何材质**，`MATE` 可整块省略。列式（P3）。

`MATE` 里**至少含条目 0（空气）**；若写方声明了一种实体材质，则 `entry_count = 2`
（空气 + 那一种）。

```
uint16  entry_count
entry[] entry_count × 12 字节
```

`entry_count` 减 1 即为可用材质的数量（`1 … entry_count−1`），其上限 `65534`
也是单个模型中不同材质值的数量上限。

> **读方不对"多余条目"报错。** 一份 `MATE` 可能含有当前 `VOX0` 未引用的条目
> （正如上）；这是合法的。校验只查"引用了不存在的条目"（§9 的 `MATE` 索引越界），
> 不查"存在未被引用的条目"——后者需要全量扫描，且无害。

### 4.1 条目（12 字节定长 → 以 `index × 12` 随机访问）

```
uint32  rgba          R<<24 | G<<16 | B<<8 | A          基色 + 不透明度
uint8   metal         0–255   金属度
uint8   rough         0–255   粗糙度
uint8   hardness      0–255   物理：抗破坏性 / 连接强度
uint8   mass          0–255   物理：密度 / 崩塌质量
uint8   e_r           0–255   自发光 R
uint8   e_g           0–255   自发光 G
uint8   e_b           0–255   自发光 B
uint8   reserved      必须为 0
```

共 **12 字节**：4（RGBA）+ 7（各 `uint8` 属性）+ 1（保留）。

- **条目 0 保留且全零。** 体素值 `0` 表示空气（`rgba = 0`）。
- 因此 **体素值 == 材质索引** 无条件成立。
- **自发光是 RGB 而非单通道强度**：霓虹、火焰、熔岩的颜色与其基色常常不同，
  单通道强度无法表达。三个 `uint8` 是表达它的最小代价。
- 物理量用 `uint8` 而非 `float32`：0–255 的分档对"硬/软""重/轻"这类游戏内
  属性完全够用，且使整个条目保持 12 字节的紧致尺寸。

> 条目大小是常量 **12**，由 `qvox` 版本定义，**不写入文件**（P2）。
> 12 字节定长 → 读者一次乘法即可索引材质。无偏移、无变长、无名称块。
> 条目不必是 2 的幂：块负载按字节寻址，`index × 12` 直接可用。
> 材质名属于编辑器元数据，不属于渲染必需数据；需要时写入方将其放入 HEAD JSON
> 的自有键，格式核心不为其引入变长结构。
>
> `reserved` 字节必须写 0，读者忽略其值。它为将来可能需要的第 8 个属性留位，
> 而不必改变条目大小——**给未来留一格，但不给现在加一分重量**。

## 5. `VOX0` —— 体素数据

列式、按块分组、自压缩。

```
uint16  model_id          模型编号，供 NODE 的 kind="model" 节点引用
uint32  block_count       本模型包含的块数（只计非空块）
uint32  payload_length    block[] 的精确字节数（不含任何填充）
block[] block_count × block（§5.1）
```

> 模型头共 10 字节（`uint16 + uint32 + uint32`），**不是 4 的整数倍**。与 §5.1 的
> 块内块头同理：字段按字节寻址，不为对齐补填充（P2）。

`block_count` 看似可由遍历负载数出来（P2 的嫌疑），但它使读者**无需解析任何块负载**
即可预先分配块数组、并校验 `block_count` 与负载长度是否自洽。这属于"为 O(1) 访问
而保留的最小计数"，与 §4 的 `entry_count` 同理。

**`payload_length` 是 P4 在 `VOX0` 内部的贯彻。** 顶层块用 `length` 让读者无需理解
内容即可跳过；`VOX0` 内部同理——`block_count` 只说明"有几块"，每块虽有各自的
`payload_length`（§5.1），但**整段模型负载的总长没有**。缺了它，读者从顶层块切出的
payload 必然含顶层块的 0–3 字节尾部填充，于是"解析到哪里才算正好用完"只能退化为
模糊判断（"剩余 < 4 字节就算合法"），留下 1–3 字节的篡改灰区。

显式存 `payload_length` 后，判定退化成一次**等式比较**：

```
预期结束 = 10 + payload_length
合法   ⟺  逐块解析恰好停在 10 + payload_length 处（不能少、不能多）
```

代价恒定 4 字节/模型，换来零灰区。

`model_id` 为 `uint16`，因此文件最多可容纳 65536 个模型。它是体素数据的**编号**，
由写入方分配；`NODE` 中 `kind="model"` 的节点以同一个数值引用它。字段间不做
填充对齐——payload 按字节寻址，无需对齐（P2：不为对齐引入无意义的填充字节）。

**`model_id` 的约定：**

- **一个 `VOX0` 块恰好对应一个 `model_id`，一个 `model_id` 恰好对应一个 `VOX0` 块。**
  两者一一对应，因此 model_id 就是这份体素数据在文件内的唯一身份。
- **必须在文件中唯一。** 出现两个相同 `model_id` 的 `VOX0` 即为损坏（§9）。
- **无需连续、无需从 0 开始。** 写入方可以只用 `{3, 7, 100}`。连续编号只是常见
  情形，不是要求——**要求编号连续会强迫写入方在删除一个模型后重排所有编号**，
  那是不必要的耦合。
- **`VOX0` 块在文件中的顺序不影响语义。** 读者应当按 `model_id` 建表，而非假设
  第 N 个 `VOX0` 就是 `model_id = N`。
- **没有对应 `VOX0` 的 `model_id`**：`NODE` 中引用了不存在的 `model_id`，视为该
  节点损坏（跳过该节点，而非拒绝文件）。

### 5.1 块

```
int32   bx, by, bz        块坐标（**块索引**，非体素坐标）
uint8   codec             块级编解码（§5.2）——先说明"是什么"
uint32  payload_length    负载字节数（不含尾部填充）
byte[]  payload
```

**块内不做对齐填充**：`payload_length` 就是实际字节数，下一个块紧接其后。
只有**顶层块**（§1.2）才有 4 字节对齐与填充——对齐是文件系统级的事，
在已被读入内存的 payload 内部没有意义。

**块坐标是块索引**：`bx` 为 1 表示沿 X 轴前进**一个整块**（`block_size` 个体素），
而不是前进 1 个体素。换算关系（`B` = HEAD 的 `block_size`）：

```
块 (bx,by,bz) 覆盖体素区间   [bx·B, bx·B + B) × [by·B, by·B + B) × [bz·B, bz·B + B)
体素 (vx,vy,vz) 所属块        (vx >> log₂B, vy >> log₂B, vz >> log₂B)
块内局部坐标                  (vx & (B−1), vy & (B−1), vz & (B−1))
```

之所以存块索引而非体素坐标：体素坐标 = `块索引 × B`，可由 `block_size` 推导，
存它就是双存（P2）。块索引还让坐标数值小 5 个数量级，varint 化后更省。

**块坐标可为负。** `bounds` 描述的是**体素**范围，块索引由它按 `块索引 = 体素 >> log₂B`
（向负无穷取整）导出，因此 `bounds` 跨越原点时块索引自然为负。若 HEAD 未给出
`bounds`（无界），任何 `int32` 范围内的块坐标都合法。**若给出了 `bounds`，则任何
块坐标经"块 → 体素区间"换算后必须完全落在 `bounds` 之内**；落入界外的块按
**块级处置**丢弃（`DROP_BLOCK`，§9），**不拒绝整个文件**——`bounds` 是写入方的
空间意图声明，个别块越界只说明这几个块不可信，其余块仍然可用。

字段顺序与外层块头同构：先身份（`codec` / 坐标），再长度，最后负载。
与顶层块头一样，**长度在负载之前**（P4）。

> 块头共 17 字节（`3×int32 + uint8 + uint32`），不是 4 的整数倍。这**不是疏漏**：
> `codec` 只有 1 字节，若为凑对齐而给它补 3 字节填充，就等于让每个块平白多付
> 3 字节，违背 P2。负载按字节寻址，本就不需要对齐——**一致性优先于对齐**。

块尺寸取自 HEAD 的 `block_size`，**不在此重复存储**（P2）。

**列式方向**：对于通道 `[material, sdf]`，负载是
`[全部 material 值][全部 sdf 值]`——连续成段，**绝不**逐体素交错。
这是 P3，也是单项最大的压缩收益。

**块是局部性与编辑的单位。** 小到可以廉价重写，大到足以摊平头部开销。
**文件中只写非空块**——`EMPTY` 是内存中的块状态，不是一种持久化编解码（见 §5.2）。

### 5.2 块级编解码

所有编解码都沿**与 `DENSE` 相同的顺序**遍历块内体素：`idx = x + y·B + z·B²`
（即 ZXY 外层、X 最快）。这一点对 `RUN` 尤为重要——游程沿该线性下标连续铺展。
其中 `B` = HEAD 的 `block_size`，块内体素总数 `N = B³`。

**"空块"的定义**：**`channels[0]`（即 `material`）在该块内全为 0**。其余通道的
内容不影响空块判定——一个 `material` 全零、但 `sdf` 非零的块，就是一个空块，
那些 `sdf` 值随之丢弃。之所以以 `channels[0]` 为准：它是**支配通道**，
决定该处是否存在可见物质；从属通道对不存在的东西没有意义。

| 编解码 | 值 | 负载 | 胜出场景 |
|---|---|---|---|
| `EMPTY` | 0 | —— **保留值，永不写入文件** | —— |
| `SOLID` | 1 | 支配通道一个值（当前单通道 bpp=16 → 2 字节） | 均匀填充 |
| `RUN` | 2 | `uint32 count` + `count ×(varint 游程长度, 通道值)` | 层状／条纹结构 |
| `DENSE` | 3 | `N × bpp/8` 字节，ZXY 顺序 | 高熵噪声 |
| `INDEXED` | 4 | `uint8 n` + n 个材质索引（各 2 字节）+ `N × max(1,⌈log₂n⌉)` 位 | 少量不同取值 |

值 `0` 被**保留**给 `EMPTY`：读者若在文件中读到 `codec=0`，应视为数据损坏
（处置为 `DROP_BLOCK`，§9.0 —— 块头里的 `plen` 已读到，下一个块的位置不受影响，
故波及范围只到这一块）。之所以保留而非从枚举中剔除，是为了让"内存中的块状态"与
"文件中的编解码"共用一套枚举——内存里每个块都有 `EMPTY` 态，文件里则用**块坐标的
缺失**表示它（§5.1），读写两端的判断逻辑因此完全一致。空块**不付任何字节，
连块头都不付**。

**`SOLID` 的负载 = 支配通道的 `bpp/8` 字节**，不是固定 1 字节。当前单通道
`material`（bpp=16）时为 2 字节。

`SOLID` 是整个性能故事的核心：真实数据里绝大多数可见块命中它，
算上 17 字节的块头与 2 字节负载，单通道时每块仅 19 字节。
写入方挑选最小的编解码；读者按字节分发。

> **`INDEXED` 不携带材质值本身**，只携带**指向 `MATE` 的索引**（`n ≤ 255`）。
> 材质的真实内容在 `MATE` 中只存一次（P2）；`INDEXED` 只是在块内重复引用它们。
> 若文件连 `MATE` 都没有（即全为空气），则不存在任何非空块，`INDEXED` 自然不出现。
> 每体素位宽取 `max(1, ⌈log₂n⌉)`——`n=1` 时是 1 位而非 0 位（0 位字段是无意义的
> 边界，且单值块本就会被 `SOLID` 抢先）。`n` 上限 255 也是该块内不同材质值个数的上限。

**`RUN` 的不变量**：所有游程长度之和**必须等于 `N`**；`count` 为游程段数，
由写入方给出，其值必须使得读取恰好消耗 `payload_length` 字节。读者若发现
游程之和不等于 `N`、或读取越过 `payload_length`，即判定**该块**损坏并跳过
（§9.0 判据：每块自带 `plen`，其余块的位置不受影响 → `DROP_BLOCK`，非 `DROP_MODEL`）。

## 6. `CACH` —— 派生数据

**由一条规则定义：`CACH` 块可以在任何时刻删除，语义影响为零。**

```
char[4] kind          任意的 4 字符标签，兼作命名空间，由写入方定义
uint16  algo_version  派生算法在 `kind` 命名空间内的版本
uint16  source_count  依赖的来源块个数
uint32  source_crc[]  source_count 个来源块的 CRC32，升序排列且去重
byte[]  payload       余下的全部字节（含块尾填充）
```

四个字段共 10 字节**定长前置**（`source_crc[]` 长度为 `4 × source_count`），
其后直到块尾（含尾部填充）即缓存内容——**由外层块头的 `length` 界定，内部不再
重复存储**（P2）。读者从块头取 `length`，减去 `10 + 4×source_count` 字节，
剩余即缓存内容（其中至多 3 个尾部零字节是填充）。这与 `HEAD`（整段 JSON 就是
payload）是同一套读法：**长度来自块头，内容随之而来，无需内部再记长度**。

**为什么 `source_crc` 是一个数组，而不是一个值？** 因为真实的派生数据很少只依赖
一个块。一个"整模型简化网格"缓存依赖该模型的**全部**非空块；一个"邻域查询加速"
结构依赖一整片区域。若只存单个 CRC，写入方只能在两件坏事里选一件：存全部来源的
异或（碰撞即错误失效）或只存第一个来源（其余变更时不失效）。**列出全部来源，
"缓存是否过期"就变成一个精确的集合比较**——这正是它应当是的。

**失效是自动且彻底的：**

1. 当前来源集合（按同一规则算出的升序去重 CRC 列表）与该数组不一致 → 丢弃，重算。
2. `(kind, algo_version)` 组合读者不认识 → 丢弃，重算。
3. `kind` 不认识 → 丢弃。
4. `source_count` 使 `10 + 4×source_count > length` → 该块损坏，跳过（§9）。

> 比较是**集合比较**，不是顺序比较：数组中 CRC 升序去重，因此同一组来源无论
> 写入顺序如何都产生相同表示。

> `algo_version` 的语义是"**在 `kind` 这个命名空间内**的算法版本"。不同写入方
> 使用各自的 `kind` 标签，因此它们的版本号互不冲突。

> 忽略所有 `CACH` 块的读者，产出与用满全部缓存的读者**完全相同**——只是
> 预热更慢。这不是约定，而是这个块类型的定义。

由于缓存绝不持有其来源中不存在的信息，本格式不存在"这是权威数据还是过期数据？"
这个问题。整整一类 bug 被设计掉了。

`kind` 的含义完全由写入方与读者商定——格式本身不解释它。一个常见的用法是让
写入方缓存自己渲染器所需的任何中间结果（例如某种降采样、简化网格、查询加速
结构），并在源数据变更时自动作废。格式对此保持中立。

## 7. `NODE` —— 场景图与动画

一个 JSON 块。以任何语言都能解析的形式取代 `.vox` 的 `nTRN`/`nGRP`/`nSHP` 三件套。

```json
{
  "nodes": [
    { "name": "root",  "kind": "group", "children": [1, 2] },
    { "name": "body",  "kind": "model", "model_id": 0, "transform": { "t": [0,0,0], "r": 0, "s": [1,1,1] } },
    { "name": "wheel", "kind": "model", "model_id": 1, "transform": { "t": [4,0,0], "r": 0, "s": [1,1,1] } }
  ],
  "layers": ["default"],
  "animations": [
    { "name": "spin", "loop": true,
      "frames": [ { "t": 0, "2": { "r": 4 } }, { "t": 100, "2": { "r": 8 } } ] }
  ]
}
```

- **节点是数组；身份即位置。** 没有 `id` 字段——下标就是 id。这去掉了一个字段
  以及整整一类悬空引用 bug。`animations` 的 `frames` 同样以**节点下标**为键
  （上例 `"2"` 即 `wheel`），全文件只有一种寻址方式。节点名是给人看的、
  可选的标签，从不参与寻址。
- `r` 是旋转索引 **0–23**（24 种轴对齐朝向），与 `.vox` 相同的编号，因此导入的
  旋转是精确的（见附录 A）。
- `kind`：`"group"`（变换容器）或 `"model"`（通过 `model_id` 绑定一个 `VOX0`，
  其值等于该 `VOX0` 的 `model_id` 字段）。
- **所有引用按下标解析，越界即该引用无效**：`children` 中的下标必须 `< nodes.length`，
  且不得形成环；`frames` 中的键必须是合法节点下标；`kind="model"` 的 `model_id`
  必须存在对应的 `VOX0`。任一引用无效时，**只丢弃该节点或该帧**，不拒绝整个文件
  （§9）——场景图是易变部分，不该因为一个坏引用毁掉整个模型。
- **单个静态模型可整块省略。** 静态场景可省略 `animations`。**缺省才是常态，且零成本。**

## 8. 读取一个文件

```
1. 读 8 字节。匹配签名，否则拒绝。
2. 读第一个块头（12 字节）。其类型必须是 "HEAD"，否则拒绝。
3. 读 length 字节，取其中 payload 部分解析为 JSON（尾部至多 3 个零字节忽略）。
   此时你已掌握全部结构性信息。
4. 循环直到文件尾，每次：
     读 12 字节块头 → 校验 CRC（可选）→ 按 type 分发
     MATE → 材质
     VOX0 → 体素（每个 model_id 一个）
     NODE → 场景图
     CACH → 忽略，或用于加速
     ???? → 什么也不做
     然后 seek 过 length 字节，到达下一块头（length 含填充，故必定对齐）
5. `VOX0` 内未出现的块坐标，一律视为空块（等价于 `EMPTY`）。
   读者无需、也无从区分"从未存在的块"与"被编辑为空的块"——两者都只是缺失。
```

**跳过的统一写法**：无论 `type` 是否认识，读完 12 字节块头后一律 `seek(length)`。
`length` 含尾部填充，因此该操作永远落在下一块的块头起点——**读者永远不需要知道
填充有多少**。这就是"块头自足"（P4）在代码里的样子。

**零解析访问（P4）**：块头自带长度与校验值，因此跳过或校验任意块都只需读
其块头。带缓存的写入方可额外提供一份目录缓存（一个 `CACH`）来实现 O(1) 查找；
没有它，线性扫描也能到达同一个块。两者都正确。

**渐进加载**：JSON 元数据位于负载之前，因此客户端可以在读取任何体素之前就呈现
场景图与材质。

**流式读取**：读 `HEAD`，然后只读取那些与视野相交的 `VOX0` 块。

## 9. 完整性

### 9.0 三档处置

一切"发现异常"的处置都落到**三档之一**，且档位由**异常的波及范围**决定，
而非由发生的层决定：

| 档 | 含义 | 触发示例 | 读者动作 |
|---|---|---|---|
| `FATAL` | 文件不可用 | 签名不匹配；块头越界；`length` 非 4 倍数；第一个块不是 `HEAD`；沿用 `HEAD` 失败；重复 `model_id` | **拒绝整个文件**（返回 null + 记录 error） |
| `DROP_MODEL` | 一个模型不可用 | `block_count` 与负载不自洽；`payload_length` 越界 | 丢弃该 `VOX0` 对应的整个模型，保留文件其余 |
| `DROP_BLOCK` | 一个块不可用 | 块 CRC 失败；块坐标落在 `bounds` 之外；块内解包失败（含 `codec=0`、游程和 ≠ `B³`、索引越界） | 丢弃该块，保留该模型其余块 |

**判据：一个异常会不会让"同一 `VOX0` 的其余块"也不可信？**

- 会 → `DROP_MODEL`（模型的块表是一个整体，块数/总长对不上时其余块也无从定位）
- 不会 → `DROP_BLOCK`（每块自带 `payload_length`，可以独立跳过）
- 连"文件里其余块是否可信"都存疑 → `FATAL`（顶层块流断了，无法继续切块）

"处置"与"层"解耦是有意的：CRC 失败发生在块层 → `DROP_BLOCK`；`block_count`
不自洽发生在模型层 → `DROP_MODEL`；签名失败发生在文件层 → `FATAL`。
**同一层可以产生不同档位的处置**，关键始终是波及范围。

### 9.1 校验表

| 层级 | 校验 | 失败处理 |
|---|---|---|
| 文件 | 8 字节签名 | `FATAL` 拒绝 |
| 块 | 逐块 CRC32（覆盖 `length` + `type` + 负载的 `length` 个字节，含尾部填充，位于块头） | `DROP_BLOCK`（跳过该块，保留其余）；**`crc==0` 表示作者未写校验值，跳过校验**（§10） |
| 语义·模型 | `block_count` 与负载自洽；`payload_length` 不越界 | `DROP_MODEL` |
| 语义·块 | VOX0 块坐标落在 `bounds` 内（若给出）；`MATE` 索引 < `entry_count`；`RUN` 游程和 == `B³` | `DROP_BLOCK` |
| 缓存 | `source_crc[]` 集合 + `(kind, algo_version)` | 丢弃缓存，重算 |

**没有文件级校验和，这是刻意的**：块可被独立校验，因此一处损坏不会牵连其余部分。

**校验分两档**：CRC32 是**结构完整性**——字节有没有被改坏；上表"语义"行是
**逻辑一致性**——字节都好好的，但字段之间互不相容（越界坐标、游程数不对、
指向不存在的材质）。**CRC 通过不意味着语义正确**，反之亦然。实现应当两档都查，
但它们的失败处理不同：CRC 失败只能跳过块；语义失败可以只丢一个模型或一个块，
保留文件其余部分。

## 10. 编码约定

- **字节序**：小端。所有多字节字段。
- **变长整数**：LEB128，仅用于 `RUN` 负载内部的游程长度。
- **字符串**：UTF-8。JSON 的边界由所属块的 `length` 界定，**从不**以 NUL 结尾。
- **对齐**：块起始 4 字节对齐（由 `length` 恒为 4 的倍数保证）；尾部零填充计入 `length`。
- **CRC 可关**：块的 `crc` 字段为 **0** 表示"作者未对本块写校验值"。读者遇到 `crc==0`
  时**跳过 CRC 校验**，直接按 `length` 跳过/读取该块。这让写入方可以在
  "体积/可读性优先"的场景（如手工调试的小文件、需要 diff 的样例）产出无 CRC 文件，
  而不必让读取端报错。真正的 CRC32 恰好为 0 的概率是 `1/2³²`，此时"少校验一次"
  的代价可忽略——这不是安全性设计，而是"作者明确声明不做校验"的表达。
- **未知块**：按 `length` 跳过。**永远不算错误**。
- **前向兼容与"必需块"**：读者遇到不认识的块类型时默认**跳过**（P1）。但某些
  未来版本可能引入"不解析就不正确"的块——它们通过 **HEAD 的 `require` 数组**声明：

  ```json
  { "qvox": 2, "require": ["SKEL"], "channels": [...] }
  ```

  读者若**无法处理** `require` 中列出的任何类型（既不是它内建的，也不认识其语义），
  应当**拒绝整个文件**，而不是静默跳过——因为跳过会导致错误的结果而非不完整的结果。
  未在 `require` 中列出的未知块一律安全跳过。**当前版本除 `HEAD` 外不定义任何必需块，
  因此 `require` 是可选的、且当前文件从不使用它。** 它为将来提供一条精确的
  "该拒绝还是该继续"的判据，而不给现在增加任何复杂度。

## 11. 完整示例 —— 一个 64³、3 材质的模型

64³ 在 `block_size=32` 下最多有 2×2×2 = 8 个块，此处只有 3 个非空。

```
89 51 56 4F 58 0D 0A 1A                              签名

[HEAD]                 length=116 type="HEAD" crc32=…   （115 字节 JSON + 1 字节填充）
  { "qvox":2, "block_size":32, "bounds":{"min":[0,0,0],"max":[64,64,64]},
    "channels":[{"name":"material","bpp":16}] }

[MATE]                 length=40 type="MATE" crc32=…    （2 + 3×12 = 38 + 2 字节填充）
  entry_count=3
  entry[0] = 全零                              （空气：rgba=0，物理量=0，无自发光）
  entry[1] = rgba=FF808080 metal=0   rough=200 hardness=80  mass=64  e=(0,0,0)
  entry[2] = rgba=FFFFD700 metal=255 rough=80  hardness=30  mass=233 e=(255,180,0)  ← 金色发光

[VOX0]                 length=112 type="VOX0" crc32=…   （10 + 3 块 = 110 + 2 字节填充）
  model_id=0 block_count=3 payload_length=110
    (1,0,0) SOLID   material=1                    →  17 + 2 = 19 字节
    (0,1,0) RUN     12 段游程                     →  17 + 24 = 41 字节
    (1,1,0) INDEXED n=2，7 位／体素               →  17 + 23 = 40 字节
    （其余 5 个块为空，不写入文件——它们不存在，即 EMPTY）

[CACH]                 length=116 type="CACH" crc32=…   （10+12+92 = 114 + 2 字节填充）
  kind="mesh" algo_version=1 source_count=3
  source_crc[] = [00FA12C4, 3B19E007, DEADBEEF]   ← 依赖 3 个 VOX0 块
```

固定开销：8（签名）+ 4×12（块头）= 56 字节。上例各块 `length` 合计
116+40+112+116 = 384 字节，整个文件 **440 字节**——承载一个 64³、3 材质、
3 个非空块的模型。其中体素实际负载仅 110 字节（含 10 字节模型头），是原始数据
（64³×2 字节 ≈ 512 KB）的 **0.02%**。这就是列式 + 块级编解码的收益。删掉 `CACH`
块（12 字节块头 + 116 字节 `length`）后文件变为 312 字节，语义完全不变（P5）。

> 上例四个块的 `length` 全是 4 的倍数（116、40、112、116），因此每块的填充
> 都不超过 3 字节，且**填充计入 `length`**——读者按键跳过时无需任何取整运算。
> 注意 `VOX0` 的 `payload_length=110` **不含**这 2 字节填充：模型头里的长度
> 描述的是 block[] 的真实字节数，尾随填充不属于模型负载。

> 注意 8 个块中只有 3 个存在于文件里。**"不存在"就是 `EMPTY` 的表示**——
> 空块不付任何字节，连块头都不付。

# 第二轮：审计出的 32 项

第一轮结束后又做了一轮独立审计（三个只读代理交叉核对，产出 A 真 bug 7 / B 重复实现 7 /
C 性能 5 / D 结构死码 13）。本节的判定标准与第一轮相同：**以"是否值得保留"为准，不以
"有没有调用点"为准**。32 项里 22 项被改掉，10 项经核实后判定"不该改"，理由逐条写在下面——
判定不改和改动一样是结论，不是跳过。

## 12. A 类：真 bug（7 项）

| # | 问题 | 处理 |
|---|---|---|
| A1 | 材质按"桶序号"绑到 surface，而非材质在数组里的实际序号 | `VoxelChunkGenerator.build_mesh_from_arrays(arrays, materials)` 改为按实际 surface 绑 |
| A2 | `VoxelCollision` 在 STATIC / `group_shift>0` 下完全不建碰撞体 | 重写为"绘制单元"抽象（见 §14） |
| A3 | `VoxelDestructionPresenter.clear_all()` 不清掉落块 RigidBody3D 与池 | 补全（见 §13） |
| A4 | `apply_block_table` 丢块分支漏 `_source_invalidated.erase` | 已修 |
| A5 | `_write_buffer_impl` 无条件预建全零缓冲 | 改为"绝不预建空缓冲" |
| A6 | 动画 fps 缺省 4 与 12 分裂 | 全仓唯一真值 `QVoxelSpec.ANIM_FPS_DEFAULT = 4` / `ANIM_LOOP_DEFAULT = true` |
| A7 | 视点层"移动时清零计数"把扫描与卸载两个周期绑死 | 拆成 `_frames_since_scan` / `_frames_since_unload` |

A2 的根因值得记：碰撞组件本身没写错，错的是**它默认"只有 per-chunk 模式才有碰撞体"**，
而默认模式恰好是 STATIC —— 于是新项目开箱即用没有碰撞，且没有任何报错。
重写后统一到"绘制单元"（unit）概念：STATIC → 一个 unit（整份 mesh 一个 body，一次性 trimesh）；
DYNAMIC+group_shift>0 → 每个 group 一个 unit；否则每个 chunk 一个 unit。判据只剩一条
`_is_per_chunk()`，三种模式各自"往哪个 unit 塞哪个 mesh"由 `_unit_of` / `_apply_unit` 决定。
同时删掉了 `_supports_chunk_collision()` —— 它带来的"不支持就静默不建"正是 A2 的成因。

## 13. B 类：重复实现（7 项）

- **B8** 装入块缓冲的三份拷贝 → `_install_block_buffer(chunk_key, buf, known_count = -1)`
- **B9** 删块的四个变体 → `_drop_chunk(ck, opts)`，opts 键：
  `cancel_async / invalidate_source / drop_lod / erase_stream / mark_mesh / mark_neighbors / keep_persist_flag`
- **B10** 碎屑"按材质分组 → 逐组发射"写了两遍 → `_group_and_emit(source, limit, mat_id_of,
  center, emission_size, cap, is_collapse)`，两处调用只差元数据（上限 600 vs 200、发射尺寸来自
  块包围盒 vs 质心、是否崩塌）
- **B11** 体素包围盒全仓第 6 份（`VoxelDestructionPresenter._voxel_bounds`，5 个调用点）→
  `VoxelWorldUtil.voxel_span(source)`，返回 `Array[Vector3i]`（空 = `[]`）
- **B12** `get_voxel` / `has_voxel` 同构 → `_probe_voxel(pos)`
- **B13** `block_size³` 手写 6 处 → `QVoxelSpec.block_volume()`
- **B14** 装体积时算 3 次 `_count_voxels` → `known_count` 参数

B11 的形状选择有理由：旧版返回 `{"min","max"}` 字典，于是"数组入参"和"字典入参"各写一套扫描。
改返回 `Array[Vector3i]` 后两种入参共用一趟扫描，且能区分"空集合（`[]`）"与"单点集合"——
字典形状下这两者都会退化成一个看似合法的包围盒。`voxel_bounds()` 保留为字典形状的薄转发
（导入 / 原点偏移 / 网格生成都按 `min`/`max` 取键）。`VoxAssetWorld` 的 `{"min","size"}`
语义不同（空模型给 1³），不并入。

## 14. C 类：性能（5 项）

- **C17** STATIC 模式为了拿一个数量建整张 chunk key 表 → `chunk_count()`，O(1)
- **C18** 每个 LOD 任务 `duplicate` 一份材质数组 → 直接传共享引用（worker 只读，零分配）
- **C19** `_process_coarse_level` 三趟遍历 + 三次求距 → 一趟枚举、一趟移除/可见性、一趟构建；
  全程用**平方距离**（`VoxelLodGrid.block_dist_sq`），只在"按距离排序"这一处开方
- **C15** flush 每次重读整个世界文件（写放大 2×）→ **判定不改**（见下）
- **C16** 视点层每轮新建整张 chunk key 表算 min/max → **判定不改**（见下）

**C15 为什么不改**：缓存"自己刚写出的字节"等于把已经删掉的 `_raw_bytes` 加回来——一份随世界
无界增长的常驻副本，而省下的只是页缓存里的 memcpy。真要省主线程时间只能把序列化搬进 worker，
但那会让"写盘在途期间 has_chunk / load_chunk 看到旧索引"，这是语义变更而不是优化。理由已写进
`_read_base_bytes` 的 doc。

**C16 为什么不该改**：实测「duplicate 2000 个 Vector3i 键 + 一趟 min/max」= **764 µs/次**，
而 `process_lod` 只在 `_cull_check_counter >= visibility_check_interval(8)` 或数据失效时才跑，
即最多 8 帧一次。为它引入 min/max 增量缓存或键表版本号，要维护 15 个 `_chunk_buffers` 写入点
（含 `shift_origin` 整表平移）——漏一处就与数据脱节，收益上限 764µs/8 帧。

## 15. D 类：结构 / 死码（13 项）

已删：`_last` 死字段、`_last_frame_delta`、`last_build_ms`、`last_trans_vertices`、
`index_vxel_blocks` 死参、4 个文件缺 `extends`、`_volume` 不变式无断言（补 `assert`）、
JSON 键名无常量（`HEAD_BLOCK_SIZE_KEY` / `HEAD_BOUNDS_KEY` / `HEAD_UP_AXIS_KEY` /
`ANIM_FRAME_DURATION_KEY` / `SCRIPT_WORLD_METHOD`）。

**D24 `affected_count`**：源码是 `_batch_rebuilt_affected += int(result.get("affected_count", 1))`，
而结果字典从来没有 `affected_count` 键 → 该字段恒等于 `last_rebuild_chunk_count`。
两个恒等的数字并排放，只会让读代码的人以为其中一个是独立算出来的。字段、累加器、下游 demo
的两处取值与日志字段一起删。

**D27 / D28「再拆文件」判定不改**：
- `QVoxelSource`（2262 行 / 167 func / 17 私有字段）按字段聚类后是**一个对象、多个连贯视图**，
  各视图大量交叉（脏账、流式、粗层互相调用），不存在可切出的独立子对象。真正能切的只有三块
  无状态汇编，而它们早已是外部类（`VoxelPointCloudExporter` / `VoxelConnectivity` /
  `VoxelPersistence`），剩余部分只是薄转发。再按职责拆会重蹈第一轮"两个视点层"的覆辙：
  包装层 + 双向依赖，而拆的是同一个不变式持有的账本。
- `QVoxelStream` 的 CACH 粗层（约 220 行）**不是死码**，且与 `_vxel_index` 高耦合
  （`_lod_expected_crcs` 读 LOD0 子块的 CRC）。拆它是把同样多代码搬到新文件、两个对象共享
  同一批字段，不产生任何解耦。**真正冗余的是"model 维度"**：本流把世界层固定为
  `LOD0_MODEL_ID = 0`，但覆盖层与墓碑照格式层的形状套了 `model_id → {chunk_key: buf}` 一层，
  于是 `_restore_inflight` 的 mid 循环、`_overlay_doc_models` 的 mid 循环、`_count_pending`
  的双层循环全是在为永远不出现的 model 1..N 服务。已压平为 `chunk_key → buf`，
  `_dirty_models: Dictionary` 收成 `_vxel_dirty: bool`，model 维度只在交给格式层的两处调用点
  临时还原。`QVoxelStream` 1013 → 1008 行，但类内 20 处 `LOD0_MODEL_ID` 取值前缀与四处多层
  遍历消失。

**D29（三模式分支收敛）/ D30（renderer 空判 helper）判定不改**：
- `has_chunk_mesh` / `chunk_mesh` 已经是统一的查询面；其余分支是"不同账本的写入端"，
  合并会把 `_lod_meshes[0]` / `_group_meshes` / `self` 三套账本压成一层间接，且要动网格热路径。
- 实测真正的 `renderer != null` 判断只有 9 处（`:90 / :94 / :100 / :132 / :201 / :212 /
  :222 / :238 / :299`），其余是各方法体里的 `r == null` 早退。为这 9 处再包一层 helper 只会更绕。

### 19.2 收掉的重复实现（4 类）

- **`ChunkVoxelCache`**："惰性 chunk 缓冲查找 + 越界安全读取"原先在 `find_unsupported_around` /
  `propagate_stress` / `collect_materials` / `patch_lod_block` / `patch_lod_block_from_lod`
  五个函数里各手写一遍，连 `local.x < 0 || ... >= CHUNK_SIZE` 的 6 项越界判断都逐字重复五次。
  现在 `at(wx, wy, wz)` 自己 ensure、局部下标由算术右移推出必在 `[0, 32)` 故无需判界、
  块缺失一律返回 0（=空气）。调用点各自的 `has_voxel` / `get_mat` / `get_voxel` lambda 全删。
- **`BulkGroups` + `group_positions_by_chunk()`**：`remove_voxels_bulk` 与 `set_voxels_bulk` 的
  "遍历 positions → 算 chunk → 算线性下标 → 算 6 位边界掩码 → 攒进 by_chunk"整段逐字重复，
  且一个用 `std::map<Vector3i>`、一个用 `unordered_map<uint64_t>`。现在共用一份：
  `struct BulkGroups { by_chunk, ck_of_key, boundary }`。掩码位定义只此一处。
- **`qvox_clip_range()` + 累加式 `qvox_crc32_run()`**：`crc32` 与 `crc32_segments` 各写一遍
  "区间裁剪"与"逐字节 `crc = (crc >> 8) ^ table[(crc ^ p[i]) & 0xFF]`"。现在 `crc32` 是
  `crc32_segments` 的单段特例，裁剪只有一份。公共语义未变（空区间仍返回 0）。
- **halo 外缘面映射**：两个 halo 构建器（降采样版 / 直接拷版）各自写了一遍 `dirs[6]`、
  `face = d.x ? 0 : (d.y ? 1 : 2)`、`fix_grid`、`halo_pos` 与三行 `if (face == ...)` 落点映射。
  现在只留 `HaloFaceInfo` + `halo_face_info()` / `halo_index_of()` / `halo_sample_origin()` /
  `halo_neighbor_index()`；两条路径的差别只剩"怎么取材质"（`downsample_cell` vs 直接拷大格）。
  这一点尤其值得抽：外缘面写错一格的表现是"相邻块接缝处多/少一层皮"，极难从现象反推。

顺带把 `chunk_of` / `buf_index` 从"支撑图失稳检测"附近（原 `:947/:983`）提到文件顶部：
它们被多个更早的函数用到，原先靠 TU 内可见性侥幸成立。

### 19.3 确认不该改

- **UV 里的 256**：`generate_dense_impl` 与 `generate_spheres_native` 各写一处
  `(float(mat_id) + 0.5f) / 256.0f`。看着像硬编码魔法数，但它等于
  `Core/VoxelMaterial.gd` 的 `MAX_MATERIAL_ID := 256`（材质纹理宽 256×1 的**调色板宽度**），
  与 `QVOX_U8_MAX = 255` 的"值上限"是两个概念。改数值会变 UV 语义，不动。
- **`build_id()`**：唯一消费者是 `NativeLoader.gd:111` 报错信息里的 `str(inst.call(&"build_id"))`。
  它正是"改了 C++ 却没重编"时唯一能看出手的那条线索，保留。
- **CACH 粗层那 ~220 行**（GDScript 侧已在 §15 判定不改）同理：与 VXEL 索引的 CRC 校验高耦合，
  拆出去等于搬同样多代码、两个对象共享同一批字段。

### 1.3 `VoxelMesher` 的两个关键设计

**① STATIC 共享 mesh 缓存** —— 这是 STATIC 收益的**全部**来源：

```gdscript
static func acquire_shared_mesh(data, scale, builder: Callable) -> ArrayMesh
static func invalidate_shared_mesh(data) -> void
```

键 = `(data 实例 id, voxel_scale)`。实测 deer×100：

| 组织方式 | draw 增量 | p50 |
|---|---|---|
| 每实例各建一份 mesh | 532 | 99.9ms（10fps） |
| **共享同一份（缓存命中）** | **4** | **6.61ms** |
| 对照：导入 ArrayMesh ×100 | 4 | 6.99ms |

**② `build_group` 的顶点平移**

单 chunk 生成是**局部坐标**（原点 = 该 chunk 角）。分组时必须按
`(ck - group_origin) × chunk_size_world` 平移，否则整组几何叠在组原点。
这是 `append_arrays(..., vertex_offset)` 参数存在的原因。

## 2. 验收数据

### 2.1 几何等价性（最重要）

`STATIC` 路径产物与导入器 `VoxelMeshGenerator.generate_mesh` **逐个模型精确相同**：

| 模型 | STATIC tri | 导入 mesh tri | 一致 |
|---|---|---|---|
| deer.vox | 1344 | 1344 | ✅ |
| cars.vox | 4638 | 4638 | ✅ |
| teapot1.vox | 39648 | 39648 | ✅ |

自动化：`test_voxel_mesher.gd::test_build_all_deer_baseline`（断言 1344）+
`test_build_group_totals_match_build_all`（分组拼装 == 整份生成）。

### 2.2 绘制单元数（teapot1，单实例，三种模式三角数全部 == 39648）

| 模式 | 绘制单元 | tri |
|---|---|---|
| DYNAMIC `group_shift=0`（重构前形态） | 158 | 39648 ✅ |
| DYNAMIC `group_shift=1`（新默认） | **35** | 39648 ✅ |
| DYNAMIC `group_shift=2` | 8 | 39648 ✅ |
| STATIC | **1** | 39648 ✅ |

⚠️ **重要边界**：deer 只有 4 个 chunk，且它们分布在 4 个**不同的组坐标**里，
所以 `group_shift=1` 时绘制单元数不降（仍 4）。分组收益只在"chunk 密集"的模型上体现
（teapot1 158→35，↓4.5×）。这不是 bug，是分组的几何本质。

### 2.3 基准场景（单模型，相机远、负载轻，两侧都接近地板）

| 负载 | 导入 mesh | DYNAMIC(1 chunk) | DYNAMIC(8 chunk) | STATIC |
|---|---|---|---|---|
| deer ×1 | 1.57ms / 1 draw | 1.32ms / 4 draw | 0.92ms / 4 draw | **0.90ms / 1 draw** |
| cars ×1 | 2.19ms / 8 draw | 1.31ms / 27 draw | 2.14ms / 14 draw | 2.21ms / 8 draw |
| teapot1 ×1 | 1.77ms / 7 draw | 1.01ms / 164 draw | （见 §2.4 注） | （见 §2.4 注） |

**STATIC 的 draw call 与导入 mesh 逐档相同**（deer 1/1、cars 8/8）——合批生效。

### 2.4 关于长跑数据的一个诚实说明

基准场景跑到 `teapot1 ×1` 之后，**窗口被编辑器遮挡触发了引擎的呈现节流**
（地板从 0.9ms 变成 6.9ms/145fps，与窗口大小、GPU 耗时无关，见
[性能实测 §6.2](渲染性能对比_QVX_vs_ArrayMesh.md)）。`teapot1 ×1` 的 group8/static 两档
因此被压在地板上（10.09 / 6.90ms），**这两格数据无效**。

`ALWAYS_ON_TOP` 已设，但本次编辑器窗口也在最前，抢不过。**不影响结论**：
关键的 draw call 对照（§2.3 前两行、§1.3 的 deer×100 微基准）都是在窗口正常时测的。

### 2.5 与导入 mesh 的直接对照（deer×100，窗口正常时）

| 组织方式 | draw 增量 | p50 |

| 基线（空场景） | 0 | 7.08ms |

## 3. 与方案的差异

### 3.1 放弃"槽位表 + 退化三角形"增量更新（被实测否决）

方案草图曾计划固定槽位 + 退化三角形做原地更新，动手第一步就被数据否掉：

- 每 chunk 顶点数极不均匀（teapot1 p50=386 / max=1625）→ 按 max 预分配浪费 **3.35 倍**显存
- `RenderingServer.mesh_surface_update_*_region` 在 Godot 4.7 **行为不可靠**：写 999 读回 `[20,21,23]`，
  字节偏移 / 索引偏移两次独立试验都不生效

→ 改为"脏了就 `clear_surfaces + add_surface_from_arrays` 整份重打包"。
实测重打包：deer 1.6~3.1ms / cars 7.4~9.3ms / teapot1 85ms。

### 3.2 `group_chunks` → `group_shift`

方案写 `group_chunks: int = 2`（每组 2 chunk/边），实现成 `group_shift: int = 1`（每组 2^1/边）。
**语义相同**，但 `shift` 与代码里的 `ck >> shift` 一致，少一层换算。

### 3.3 `VoxelPagedLayer` 的 `process_lod` 只做骨架

视锥过滤 / 延迟补建 / 流式加载卸载 / origin shift **已完整实现并实测通过**（6 组用例全过）。
LOD 粗层派发与挂载留了骨架 + TODO，原因：
- 需要数据层开新公开面（`_snapshot_lod_block_*` 目前私有）
- 旧 `VoxelInfiniteLayer` 仍在服役，并存期不该同时改粗层账本

**当前：`VoxelPagedLayer` 可用（`enabled = false` 默认关闭），接管 LOD 粗层是后续工作。**

### 3.4 组件接线状态

| 组件 | 实现 | 已接线进 `VoxelRenderer` | 验证 |
|---|---|---|---|
| `VoxelMesher` | ✅ 240 行 | ✅ **是核心依赖** | 19 个单测 + 几何等价性 |
| `VoxelCollision` | ✅ 248 行 | ✅ `generate_collision` 开关 → `collision` 懒创建子节点 | deer×1 建 4 个 body / 复用 shape / 双限流 |
| `VoxelParticleView` | ✅ 257 行 | ✅ `display_mode` → `particle_view` 懒创建子节点 | particle_demo 340fps / 19359 粒子 / 2 draw pass |
| `VoxelPagedLayer` | ✅ 524 行（4/5 能力） | ❌ 未接线 | 独立 6 组用例通过；`enabled` 默认 false |
| `VoxelDestructible` | ✅ 1000 行 | ✅ **已改为组件**（`extends Node3D`，挂 `VoxelRenderer` 下） | destruction_demo 181/181 chunk / 破坏 2344 体素生效 / 363 测试全绿 |

**`VoxelCollision` / `VoxelParticleView` 接线的关键设计：宿主保留全部公开面。**
`particle_node` / `particle_points` 变成转发 getter，`particle_*` / `voxel_shape` 等旋钮
仍是 `@export`（Inspector 唯一真值），改值时推给组件。于是 `particle_demo.gd`
**一行没改**就跑通了 340fps —— 这是"组件化不该破坏存量调用方"的验收点。

**`VoxelPagedLayer` 为什么还没接线**：它能替代 `VoxelInfiniteLayer` 的视锥/流式/补建/origin shift，
但 LOD 粗层调度（旧层 ~570 行）还是骨架。而 `destruction_demo` 用 `lod_count=3`、
`test_voxel_infinite_layer` 直接断言旧层的内部账本 —— 接线等于同时改这三处。
风险（570 行 + 私有协议 + 3 个测试）明显高于收益（功能无变化，只是消除双向依赖），
故留作可选后续。这是**可用的中间态**，不是半成品。

## 5. 实现期新踩的坑

### 5.1 STATIC 共享缓存不做就白做

第一版 `_rebuild_static()` 每实例各建一份 mesh，实测 deer×100 是 **532 draw / 10fps** —— 比不改还差。
**收益 100% 来自"多实例共享同一份资源 → 引擎自动合批"**，缓存是必需品不是优化。

### 5.2 100 个实例各自生成一遍材质

`_update_mesh` 原本无条件调 `_materials.surfaces()`（生成 4 张 256×1 纹理）。
STATIC 下 100 实例各生成一遍，实测多花 **400ms**。改为只由第一个构建者在 builder 闭包里生成。

### 5.3 分组模式的重建永远不触发

`_process` 里原本只判 `_mesh_build_queue` 非空才 `call_deferred("_process_mesh_build_queue")`。
分组路径结果全进 `_group_dirty`，**不判它 → 整组重建永不发生**（表现为组数 0、画面空白）。
修法：`if (not _mesh_build_queue.is_empty() or not _group_dirty.is_empty())`。

### 5.4 STATIC 仍在跑视点调度

第一版 `_process` 无差别跑 `process_lod` / `process_streaming`。STATIC 实例每帧仍付一遍视点扫描
（deer×1000 实测多花约 1.1ms/帧）。修法：`if draw_mode == DrawMode.STATIC: _drive_static(); return`。

### 5.5 `has_chunk_mesh` 三模式化会破契约测试

内核契约测试冻结了 28 个公开方法名。新增 `chunk_mesh()` 必须同步改契约清单 —— 这正是那份测试的价值。

### 5.6 【最严重，已修】分组重建在主线程 + 几何生成两遍

这是本次重构里**最严重的一次回归**，症状是用户报的："destruction_demo 等半天模型显示不全"
"water_demo 随机事件一增加性能直线下降"。

**根因（双重缺陷叠加）**：

```
【第一版分组路径】
  子线程 worker 生成 per-chunk 几何  →  【丢弃】→ 只记一个 _group_dirty 标记
  帧尾【主线程】用 VoxelMesher.build_group 从体素【重新生成】整组所有 chunk
```

1. **几何算两遍**：worker 已经（带 34³ 光环）算好的正确几何被丢掉，白算一次。
2. **第二遍在主线程**：`build_group` 每组 2~8ms，而帧尾预算只有 8ms。
   destruction_demo 是 196 chunk / 32 组 → 光初始全量就要 10+ 帧，
   而 `continuous_interval=3` 还在持续破坏 → **脏组永远追不上 → 模型永远显示不全**。

**修法（两步）**：

1. **缓存 worker 的产出**（`_chunk_arrays: chunk_key → arrays`），帧尾只做**纯拼接**
   （顶点平移 + 索引偏移）。实测单组拼装 **0.38ms**（对比重新生成的 2~8ms）。
2. **`group_shift` 默认值改回 0**（= 重构前字节等价）。分组是显式 opt-in：
   它把整组重建放主线程，只在"多实例共享"或"chunk 密集且编辑不频繁"时划算。

**修复前后实测（destruction_demo，同一台机）**：

| | fps | lod0 填充 | tris |
|---|---|---|---|
| 第一版（分组 gs=1，主线程重生成） | 未完成（长期 24/32 组） | 24/32 | 8360 |
| **修复后（gs=0，per-chunk）** | **48** | **181/181** | 23068 |

**验证依据**：把改动 stash 回 HEAD 版本重跑同一场景，fps 42 / lod0 181/181 / tris 23068 ——
与修复后的数字一致（48 vs 42 是测量波动），**证明没有性能退化**。

### 5.7 water_demo 的"随机事件掉帧"与渲染无关

用户的第二个报告经测量是**误判**：

| 指标 | 数值 | 结论 |
|---|---|---|
| 关掉 `renderer.set_process(false)` 前后帧时间 | 11.47ms → 11.43ms | renderer 开销 **0.04ms** |
| 水模拟自身 `_gen_time` | 24~33ms | 瓶颈在这里 |

`water_sim.gd::_update_water()` 是每帧 `get_positions()` 全遍历 + 逐体素 6 邻居查询的
**O(n) 元胞自动机**（n = 全部体素，2170~3158 个）。这是 demo 自身的算法成本，
与 `VoxelRenderer` 无关 —— 重构前后都是这个量级。

> 【更正】先前我把一条 `Cannot call method 'get' on a null value` 的堆栈误归因为 water_sim 的
> 既有 bug。回溯栈顶帧 `[0] _mcp_run` 可知那是**我自己的 eval 脚本**在 scene 为 null 时调 `.get()`，
> water_sim 的 `_process` 只是当时引擎恰好执行到的位置。**water_sim 没有这个 bug**，特此更正。

### 5.8 教训

**给"两套策略"加默认值时，必须把所有存量调用方按语义分一遍类。** 逐点核对结果：

| 调用方 | 是否编辑体素 | 该用 |
|---|---|---|
| `particle_demo` / `qvox_model_viewer` / `qvox_vs_mesh_compare` | 0 处 `set_voxel` | STATIC 正确（默认值即可） |
| `VoxelDestructible` 全部子场景 | 高频编辑 | **DYNAMIC gs=0（`_init` 兜底）** |
| `demo/water_sim.gd` | 逐帧批量 | **DYNAMIC gs=0（已显式）** |
| `demo.tscn`（静态展示 deer/cars/teapot） | 0 处 | STATIC 正确 |
| 测试（kernel_contract / infinite_layer / runtime_smoke） | 各自显式设 | 显式或 DYNAMIC |

**第二条教训**：新增的"整组重建"路径必须确认它**没有把已有工作丢掉重做**。
`_apply_built_chunk` 拿到的 `entry["arrays"]` 是 worker 已经算好的成品，
任何"我再算一遍"的想法都要先问"为什么已有的不能直接用"。

### 5.9 编辑延迟的构成（不是重建慢）

`VoxelDestructible` 单次编辑从 `set_voxel` 到"网格已更新"实测 **1~3 帧**，而
整组拼装本身只要 **0.38ms**。差额全在流水线延迟：
`data.changed` → 下一帧 `_process` 派 worker → worker 完成 → 再下一帧帧尾应用。
**这是异步管线的正常延迟，不是性能问题。**

### 6.2.1 迁移中踩到的两个真 bug

**① 双驱动导致帧率崩塌（9 fps）**

`VoxelPagedLayer` 是 Node，`enable()` 里调了 `set_process(true)`；而宿主 `VoxelRenderer._process`
也在每帧调它的 `process_*`。于是同一轮调度**每帧跑两遍**：
`_cull_check_counter` 每帧 +2 → 实际间隔变成 `visibility_check_interval / 2`，LOD 派发成双倍洪峰。
实测 destruction_demo（181 chunk / lod_count=3）从 **51 fps 掉到 9 fps**。

修法：有宿主时 `enable()` 只设 `enabled = true` 并 `set_process(false)`（**宿主驱动，组件被动执行**）；
只有独立使用（无宿主）才自 `set_process(true)`。

**② 空快照越界崩溃**

`_lod_worker_build` 直接调 `extract_center_from_halo(halo)`。而 LOD0 数据尚未加载完成时
原生会返回**尺寸为 0 的 halo**（边界 block / 半加载状态）→ `Out of bounds get index 1191`。
这是**正常时序**（粗层 request 早于 LOD0 就绪），不是错误。

修法：worker 里判 `halo.size() != LOD_BLOCK_HALO_VOLUME` 就早退为"空结果"，让主线程走
`_lod_mark_null_or_retry` 重试计数。旧层与 `QVoxelSource._lod_downsample_worker` 有**同样**的
越界点，一并修了（是既有 bug，不是本次引入的）。

### 6.2.2 为什么允许改 `test_voxel_infinite_layer` 的断言

那个文件钉住旧层行为。接管后**旧层仍完整可用**（`paged_layer == null` 时一切照旧），
所以旧层断言全部保留；只是新增 `test_voxel_paged_layer.gd`（6 个用例）把同一套行为在
**接管路径**上再钉一遍 —— 特别是"相机远时 LOD1 必须挂出真网格"这条搬迁核心断言。
两条路径各有独立的网，等价性因此可验证而不是靠肉眼。

### 6.4 性能优化（本轮）

三处热点都在"拼接几何"这条路径上，共 3 项：

| # | 问题 | 修法 | 实测收益 |
|---|---|---|---|
| 1 | `append_arrays` 用 `dst[k] = dst[k] + src` 拼接 → 每次新建整份 PackedArray 全量拷贝，N 次追加是 **O(N²)** | 取局部引用 + `append_array`（均摊 O(m)） | 64 chunk 组：**1.87ms → 1.10ms（1.7×）**；组越粗差距越大 |
| 2 | `build_group` 在 GDScript 里逐顶点加平移量（teapot1 共 72610 顶点 × 158 chunk） | 原生 `generate_chunk_dense` 的 `offset` 参数本来就是这个语义（**单位=体素，内部乘 scale**），直接把相对偏移叠上去 | 平移成本 **1.62ms → 0** |
| 3 | `_rebuild_static` 用 `surface_get_arrays()` 数三角形填诊断字段 | 该 API 会为整个 surface **复制一份新字典**（顶点/法线/UV/索引全重建）。改用已算好的 `arrays` 直接读尺寸 | 省 **6.25ms / teapot1**（一次多余的全份几何拷贝） |

**为什么第 3 条值得单独说**：它不影响画面、不影响正确性，纯粹是"为了填一个 HUD 数字，
在建立网格的同一帧把几何又拷了一遍"。这类开销在性能剖析里最容易被漏掉 ——
因为它藏在"统计"里，看起来不像是热路径。

**验证**：三处改动后 `last_solid_vertices=72610 / last_total_chunks=158 / tris=39648`
与导入器逐位一致；headless 363/363 全绿。
